# 文法扩展方案：自增运算符 `++`

状态：修改建议，尚未实施。本文按“词法 → AST → 解析 → 语义 → 验收”的顺序给出改法，包含完整 AST 参考类、完整 `parseUnaryExp()` 和 `analyzeInc()`。返回[示例目录](README.md)。所有文件路径均相对于项目根目录。

下文完整代码以**只加入 `++`** 为前提；若已经实施 `~`、`+=` 等扩展，合并相应分支，保留已有功能。本文中的“替换方法”“增加字段”均为未来实施指引，本次只修改文档。

## 1. 先确定扩展规则

当前代码只支持词法、语法、语义分析，中间代码和目标代码生成尚未实现（见 `src/utils/Controller.java`）。因此当前可完成的是识别、构建 AST 和语义检查；运行时更新变量属于未来代码生成阶段。

本文建议同时支持以下形式，属于本项目的扩展设计，并非现有课程文法要求：

| 形式 | 写回变量 | 表达式的值 |
| --- | --- | --- |
| `++i` | `i` 加 1 | 更新后的值 |
| `i++` | `i` 加 1 | 更新前的值 |
| `++a[k]`、`a[k]++` | 指定数组元素加 1 | 同样区分前置、后置 |

新增两条产生式，保留原有 `UnaryExp` 候选式：

```text
UnaryExp -> PrimaryExp
          | Ident '(' [FuncRParams] ')'
          | UnaryOp UnaryExp
          | '(' BType ')' UnaryExp
          | '++' LVal
          | LVal '++'
UnaryOp -> '+' | '-' | '!'
LVal -> Ident ['[' Exp ']']
```

`++` 直接作用于 `LVal`，因此本方案只需扩展 `UnaryExp`，不用新增表达式优先级层或 `IncStmt`。主要约束：

- 操作数限定为现有 `LVal`，即变量名或一维数组元素；不支持 `(i)++`、`++(i)`、`f()++`、`1++`、`++(i + 1)`。
- 目标必须是可修改的 `int` 或 `char` 标量，不能是常量、整个数组或函数。
- 结果类型沿用目标类型，以适配仓库现有的严格类型检查；`char` 更新时按现有无符号字符规则截断，即 `& 0xFF`。
- 前置、后置结果均作为普通值使用，不再次作为自增目标；拒绝 `++++i`、`i++++`、`++i++`。
- 自增具有副作用，不允许出现在要求编译期常量的上下文。
- 本方案不加入 `--`、`+=` 或 `for`，它们需要各自定义规则。

前置和后置的**目标限制、类型、错误检查完全相同**，只有将来执行时返回旧值还是新值不同。现在通过两个 AST `Kind` 保存这个区别，语义阶段共用一个 `analyzeInc()`。

普通 `UnaryOp` 仍只有 `+`、`-`、`!`，不把 `++` 填进 `UnaryOp`。原有相邻相同普通单目限制继续保留：`+ +i` 仍报 `e`；连续字符 `++i` 则会识别成独立自增 token。这项词法变化属于扩展契约。

## 3. 词法分析：将 `++` 识别为一个 token

### 3.1 `src/frontend/token/TokenType.java`

在 `Plus("PLUS")` 附近增加：

```java
Inc("INC"),
```

`INC` 是本文建议的输出名称，并非原课程规定的 token 名称。

### 3.2 `src/frontend/Lexer.java`

当前 `+` 通过 `Symbols.TABLE` 的单字符映射识别，`++` 会得到两个 `Plus`。在 `readOp()` 的 `switch (c)` 中，增加专门分支，放在 `default` 之前：

```java
case '+' -> {
    int next = reader.read();
    if (next == '+') {
        addToken(TokenType.Inc, "++", start);
    } else {
        reader.unread(next);
        addToken(TokenType.Plus, "+", start);
    }
}
```

复用当前 `start` 记录首个 `+` 的位置。`Reader.unread(-1)` 已处理文件末尾，无需额外回退逻辑。`Symbols.TABLE` 的键是 `Character`，不能往里面添加字符串 `"++"`；保留原来的 `'+'` 映射即可。

若已实现 `+=`，不要再写第二个 `case '+'`；在同一分支按第二个字符区分 `+`、`=` 和其它情况，具体合并代码见[复合赋值方案](文法扩展-复合赋值.md)。

采用最长匹配，只合并相邻字符：

| 输入 | 关键 token 切分 |
| --- | --- |
| `i++` | `Ident Inc` |
| `++i` | `Inc Ident` |
| `i + +j` | `Ident Plus Plus Ident` |
| `i+++j` | `Ident Inc Plus Ident`，即 `(i++) + j` |
| `i + ++j` | `Ident Plus Inc Ident` |
| `i+/*注释*/+j` | `Ident Plus Plus Ident`，不能跨注释合并 |

后续是否合法由语法、语义决定。例如原有“相邻普通单目运算符不能相同”的规则仍会拒绝 `+ +i`。

## 4. AST：保留前置、后置和目标信息

### 4.1 新节点保存什么

修改文件：`src/frontend/ast/expression/UnaryExp.java`。

| 输入 | `kind` | `target` | `incToken` |
| --- | --- | --- | --- |
| `++i` | `PreInc` | 名称为 i 的 `LVal` | 前面的 `++` token |
| `i++` | `PostInc` | 名称为 i 的 `LVal` | 后面的 `++` token |
| `a[k]++` | `PostInc` | 名称为 a、下标为 k 的 `LVal` | 后面的 `++` token |

`target` 保存“修改谁”，`incToken` 保存诊断位置，`kind` 保存前后置区别。自增节点的 `op` 和 `operand` 为 null；这两个旧字段仍只用于普通单目运算 / 转换。

### 4.2 完整的 `UnaryExp.java` 参考版本

本方案保留原有七参数构造器和四个工厂的调用方式，只让原构造器把两个新字段设为 null；另加一个三参数构造器专门创建自增节点。这样无需逐个改动旧工厂的参数列表。

下面是包含旧功能的完整参考类，可以对照修改本文件；若已有 `~` 的 `calculateUnary()` 分支，请保留它。

```java
package frontend.ast.expression;

import frontend.ast.ASTNode;
import frontend.token.Token;
import frontend.token.TokenType;

public class UnaryExp extends ASTNode {
    public enum Kind {
        Primary, Call, Unary, Cast, PreInc, PostInc
    }

    private final Kind kind;
    private final PrimaryExp primary;
    private final Token ident;
    private final FuncRParams params;
    private final UnaryOp op;
    private final Token castType;
    private final UnaryExp operand;

    private final LVal target;
    private final Token incToken;
    private boolean charResult;

    // 原有节点：保留原构造器签名，新增字段设为 null。
    private UnaryExp(Kind kind, PrimaryExp primary, Token ident, FuncRParams params,
                     UnaryOp op, Token castType, UnaryExp operand) {
        this.kind = kind;
        this.primary = primary;
        this.ident = ident;
        this.params = params;
        this.op = op;
        this.castType = castType;
        this.operand = operand;
        this.target = null;
        this.incToken = null;
    }

    // 新增节点：只保存前后置种类、目标和 ++ 的位置。
    private UnaryExp(Kind kind, LVal target, Token incToken) {
        this.kind = kind;
        this.target = target;
        this.incToken = incToken;
        this.primary = null;
        this.ident = null;
        this.params = null;
        this.op = null;
        this.castType = null;
        this.operand = null;
    }

    public static UnaryExp primary(PrimaryExp primary) {
        return new UnaryExp(Kind.Primary, primary, null, null, null, null, null);
    }

    public static UnaryExp call(Token ident, FuncRParams params) {
        return new UnaryExp(Kind.Call, null, ident, params, null, null, null);
    }

    public static UnaryExp unary(UnaryOp op, UnaryExp operand) {
        return new UnaryExp(Kind.Unary, null, null, null, op, null, operand);
    }

    public static UnaryExp cast(Token castType, UnaryExp operand) {
        return new UnaryExp(Kind.Cast, null, null, null, null, castType, operand);
    }

    public static UnaryExp preInc(Token incToken, LVal target) {
        return new UnaryExp(Kind.PreInc, target, incToken);
    }

    public static UnaryExp postInc(LVal target, Token incToken) {
        return new UnaryExp(Kind.PostInc, target, incToken);
    }

    public Kind getKind() {
        return kind;
    }

    public PrimaryExp getPrimary() {
        return primary;
    }

    public Token getIdent() {
        return ident;
    }

    public FuncRParams getParams() {
        return params;
    }

    public UnaryOp getOp() {
        return op;
    }

    public Token getCastType() {
        return castType;
    }

    public UnaryExp getOperand() {
        return operand;
    }

    public LVal getTarget() {
        return target;
    }

    public Token getIncToken() {
        return incToken;
    }

    public void setCharResult(boolean charResult) {
        this.charResult = charResult;
    }

    @Override
    public int calculateConst() {
        int value = switch (kind) {
            case Primary -> primary.calculateConst();
            case Call -> throw new UnsupportedOperationException(
                    "函数调用 `" + ident.value() + "` 没有编译期值");
            case Unary -> calculateUnary();
            case Cast -> cast(operand.calculateConst(), castType);
            case PreInc, PostInc -> throw new UnsupportedOperationException(
                    "自增表达式具有副作用，不能进行编译期常量求值");
        };
        return charResult ? value & 0xFF : value;
    }

    private int calculateUnary() {
        int value = operand.calculateConst();
        return switch (op.getToken().getType()) {
            case Plus -> value;
            case Minus -> -value;
            case Not -> throw new UnsupportedOperationException("常量表达式中不能出现逻辑非");
            default -> throw new UnsupportedOperationException(
                    "一元运算符 " + op.getToken() + " 没有编译期值");
        };
    }

    public static int cast(int value, Token castType) {
        if (castType.is(TokenType.Int)) {
            return value;
        }
        if (castType.is(TokenType.Char)) {
            return value & 0xFF;
        }
        throw new IllegalArgumentException("期望 int 或 char 转换，实际是 " + castType);
    }

    @Override
    protected String getName() {
        return "<UnaryExp>";
    }
}
```

这里抛出求值异常，是为了防止自增被当成纯常量计算。真正写入 `error.txt` 的诊断仍由第 6 节负责；`ConstFolder.fold()` 捕获异常返回 null，不会自己报告错误。前端也不能在此修改符号表中的变量值。

## 5. 语法分析：接入现有表达式链

### 5.1 替换 `atExpressionStart()`

修改文件：`src/frontend/Parser.java`。完整方法如下：

```java
private boolean atExpressionStart() {
    return among(TokenType.Inc, TokenType.Plus, TokenType.Minus, TokenType.Not,
            TokenType.LParen, TokenType.Ident, TokenType.IntConst, TokenType.CharConst);
}
```

加入 `Inc` 是为了让 `return ++i;`、`f(++i)` 的可选表达式入口真正调用解析器。数组长度中的自增也要先成功解析，再由常量上下文检查报错。若已添加 `~`，同时保留 `TokenType.Tilde`。

### 5.2 替换完整的 `parseUnaryExp()`

```java
private UnaryExp parseUnaryExp() {
    // 1. 前置：遇到 ++ 后直接读取一个 LVal。
    if (among(TokenType.Inc)) {
        Token op = consume(TokenType.Inc);
        LVal target = parseLVal();
        return watch(UnaryExp.preInc(op, target));
    }

    // 2. 保留普通单目运算，其操作数仍递归解析 UnaryExp。
    if (among(TokenType.Plus, TokenType.Minus, TokenType.Not)) {
        UnaryOp op = watch(new UnaryOp(consumeAny(
                TokenType.Plus, TokenType.Minus, TokenType.Not)));
        return watch(UnaryExp.unary(op, parseUnaryExp()));
    }

    // 3. 保留显式类型转换。
    if (among(TokenType.LParen) && among(1, TokenType.Int, TokenType.Char)) {
        consume(TokenType.LParen);
        Token castType = parseBType();
        consume(TokenType.RParen);
        return watch(UnaryExp.cast(castType, parseUnaryExp()));
    }

    // 4. 函数调用必须放在普通标识符 / 后置自增分支之前。
    if (among(TokenType.Ident) && among(1, TokenType.LParen)) {
        Token ident = consume(TokenType.Ident);
        consume(TokenType.LParen);
        FuncRParams params = atExpressionStart() ? parseFuncRParams() : null;
        consume(TokenType.RParen);
        return watch(UnaryExp.call(ident, params));
    }

    // 5. 先读完整 LVal，再看它后面是否紧跟 ++。
    if (among(TokenType.Ident)) {
        LVal target = parseLVal();
        if (among(TokenType.Inc)) {
            Token op = consume(TokenType.Inc);
            return watch(UnaryExp.postInc(target, op));
        }
        // 普通 i / a[k] 仍需输出 PrimaryExp，保持原有轨迹。
        return watch(UnaryExp.primary(watch(PrimaryExp.lval(target))));
    }

    // 6. 其余主表达式：括号表达式、整数 / 字符常量。
    return watch(UnaryExp.primary(parsePrimaryExp()));
}
```

只需替换这两个方法，保留 `parsePrimaryExp()`、`parseLVal()`、`parseMulExp()` 等其余方法。若已实现 `~`，在第 2 个分支的 `among` 和 `consumeAny` 中同时保留 `Tilde`。

### 5.3 为什么这样组织分支

| 设计 | 原因 |
| --- | --- |
| 前置分支读取 `parseLVal()` | 语法上只允许修改变量 / 数组元素，直接拒绝 `++1`、`++(i)`、`++++i` |
| 标识符分支先读取完整 `LVal` | 后置 `++` 可能在 `a[f()]` 的右方括号之后，不能只看标识符后一个 token |
| 函数调用先于标识符分支 | 否则 `f(...)` 会提前被当成普通变量 f |
| 普通标识符额外 `watch(PrimaryExp.lval(...))` | 自增分支接管了标识符入口，但普通变量仍须保留原 `<PrimaryExp>` 层 |
| 普通单目分支继续递归 | `-i++` 可以解析为对 `i++` 的取负；`++i * 2`、`i++ + 2` 也自然进入原有乘加层 |

新增文法是 `UnaryExp -> LVal '++'`，因此直接自增节点不经过 `<PrimaryExp>`。例如表达式 `i++` 对应的局部语法轨迹是：

```text
IDENFR i
<LVal>
INC ++
<UnaryExp>
```

普通 `i` 则仍是 `IDENFR i` → `<LVal>` → `<PrimaryExp>` → `<UnaryExp>`。这两种轨迹的区别由产生式决定，不应人为补齐成同一种。

### 5.4 语句与回溯无需新分支

`i++;`、`++i;` 都能复用 `Stmt → [Exp] ';'` 和现有 `ExpStmt`。`isAssignStmt()` 试解析 `LVal` 后只有看到 `=` 才判为赋值；遇到 `Inc` 会恢复 token、错误表和 watcher，然后按表达式语句解析。因此不必新增 `IncStmt`，也不必修改 `parseLVal()`。

`consume()` 只为缺少 `;`、`)`、`]` 提供恢复；对于 `++1`、`f()++` 等本方案不支持的形式，当前框架可能抛出解析异常并中止，不能声称已经具有通用语法错误码。若要求这些输入也输出结构化诊断并继续解析，需要另行设计通用语法诊断与恢复，本方案不借用 `a` 或 `i` 冒充它。

## 6. 语义分析：检查目标是否可修改

### 6.1 `src/frontend/Traverser.java`

**第一处：替换完整的 `analyzeUnaryExp()`，保留原有四种分派，新增两种自增分派。**

```java
private Type analyzeUnaryExp(UnaryExp exp, boolean constContext) {
    if (exp == null) {
        return null;
    }
    Type cached = types.get(exp);
    if (cached != null) {
        return cached;
    }
    Type type = switch (exp.getKind()) {
        case Primary -> analyzePrimaryExp(exp.getPrimary(), constContext);
        case Cast -> analyzeCast(exp, constContext);
        case Unary -> analyzeUnaryOp(exp, constContext);
        case Call -> analyzeCall(exp, constContext);
        case PreInc, PostInc -> analyzeInc(exp, constContext);
    };
    put(exp, type);
    return type;
}
```

**第二处：在该方法后增加完整的 `analyzeInc()`。** 现有文件已导入需要的类型，代码依赖第 6.3 节的扩展错误枚举。

```java
private Type analyzeInc(UnaryExp exp, boolean constContext) {
    LVal target = exp.getTarget();
    // 按本文 AST 工厂约定，target 和 incToken 均非 null。
    // 先按普通左值解析，常量上下文限制由本节点单独处理。
    Type type = analyzeLVal(target, false);
    SymbolVariable symbol = target.getSymbol();
    boolean valid = type != null;

    if (symbol != null && symbol.isConst()) {
        errors.add(ErrorType.AssignToConstant, target.getIdent().location());
        valid = false;
    }

    if (type != null && !type.isBasic()) {
        errors.add(ErrorType.MismatchedParameterType, exp.getIncToken().location());
        valid = false;
    }

    if (constContext) {
        errors.add(ErrorType.InvalidConstantExpression, exp.getIncToken().location());
        valid = false;
    }

    // 前置、后置具有相同的类型和合法性要求，取值区别留给代码生成。
    // 此处不修改变量值，也不做常量求值。
    return valid ? type : null;
}
```

**为什么这里传 `analyzeLVal(target, false)`？** 要先按普通左值规则绑定目标，区分未定义、常量和数组。若直接传 `constContext`，普通可变变量会提前被原来的常量引用检查报成 `c`，不便报告本方案明确规定的副作用错误 `o`。最后的 `if (constContext)` 统一拒绝整个自增节点，包括目标下标中可能出现的副作用。

**为什么单独写 `analyzeInc()`？** 现有 `analyzeUnaryOp()` 主要检查值的类型；自增还必须检查目标是否可修改。这里复用 `analyzeLVal()` 做名称 / 下标分析，再增加常量修改与常量上下文检查。`i++;` 通过 `ExpStmt` 进入语义分析，不会调用 `analyzeAssign()`，因此不能依赖赋值语句已有的 `h` 检查。

**前后置在此有区别吗？** 没有。它们都返回目标类型；外层 `put()` 统一缓存类型并设置 `charResult`。前后置的取值区别保存在 `Kind` 中，等后端读取。语义分析期间不执行加 1 或写回。

现有 `analyzeLVal()` 在部分下标类型错误后仍返回元素类型，因此 `analyzeInc()` 也可能返回非空类型，但错误表已经记录 `e`；返回类型用于后续分析，不保证整个表达式合法。`checkConsecutiveUnary()` 继续负责普通单目运算，保持自增节点的 `op == null` 即可。

```java
    };
}
```

新增 `Kind` 后，`UnaryExp.calculateConst()`、`Traverser.analyzeUnaryExp()` 和这里都是必须补全的穷举 `switch`，遗漏会导致 Java 编译失败。

### 6.3 常量上下文的扩展错误

现有错误码 `a`～`n` 没有专门表示“带副作用表达式不能用于常量上下文”的类别。本文建议在扩展版本的 `src/error/ErrorType.java` 增加：

```java
InvalidConstantExpression("o"),
```

这是新扩展约定，不属于官方 `a`～`n`。`priority()` 已有 `default`，可沿用默认优先级。在 `ui/compilerui/model/DisplayError.java` 的 `chineseDescription()` switch 增加：

```java
case InvalidConstantExpression -> "常量表达式中存在非法操作";
```

诊断分工如下，单独测试各行：

| 场景 | 错误 | 由谁检查 |
| --- | --- | --- |
| `unknown++` | `c` | `analyzeLVal()` |
| `f++`，f 是已声明函数 | `e` | `analyzeLVal()` 拒绝把函数当变量 |
| `a[(char)0]++` | `e` | `analyzeLVal()` 的下标类型检查 |
| `k++`，k 是常量 | `h` | `analyzeInc()` 的 `symbol.isConst()` |
| `a++`，a 是整个数组 | `e` | `analyzeInc()` 的 `type.isBasic()` |
| 可变 i 用于 `const int n = ++i;` / `int a[i++];` | `o` | `analyzeInc()` 的 `constContext` |

同一行只保留优先级最高的一条；等优先级保留先记录的错误。因此 `const int k = 1; const int n = ++k;` 独立触发的修改目标错误 `h` 会先于 `o`，最终不能要求同一行输出两条。需要检查 `o` 时使用可变目标，避免被 `h` 覆盖。

## 7. UI 与项目说明同步

- `ui/compilerui/pipeline/SyntaxReference.java`：在 `OPERATOR_ENTRIES` 增加 `new Entry("++", "运算符", "自增，支持前置与后置")`。它不会从单字符 `Symbols.TABLE` 自动获得 `++`。
- `ui/compilerui/pipeline/SyntaxHighlighter.java`：在 `isTwoCharOperator()` 的 `switch` 中加入 `"++"`。当前逐个 `+` 也会显示运算符颜色，但补充后才按一个双字符运算符扫描。
- 实现完成后更新 README 和设计报告，注明这是扩展语法。课程文法原文件可保留为基线，由扩展文档明确差异。
- `ParserWatcher.java` 和 `AstTreePanel.java` 通常无需修改：沿用已有 `<UnaryExp>` 和 `watch()` 机制即可。

## 8. 未来代码生成阶段的要求

当前没有可以直接修改的 IR 生成器文件，下面仅是未来实现约束：

```text
address = 求目标地址（只求一次，包含数组下标的求值）
old = load address
updated = old + 1
若目标为 char：updated = updated & 255
store updated, address
前置自增返回 updated；后置自增返回 old
```

不能简单把 `i++` 替换为 `i + 1`，因为必须写回变量；也不能只替换成赋值语句，因为表达式还要产生正确结果。

本扩展约定 int 的 `old + 1` 按 32 位环绕；char 按现有无符号字符规则截断到 0～255。上述 load / store 是未来后端的步骤，不能搬进当前语义分析器。

对 `a[i++]++`，必须只求一次下标，使用原来的 `i` 定位元素，同时让 `i` 只增加一次。`&&`、`||` 的右侧若被短路，里面的自增不能执行。未来还应定义表达式操作数的求值顺序；当前不要用 `i++ + ++i` 这类样例作为运行时数值验收依据。

## 9. 实现后的验收用例

以下为实施后的预期，不表示当前编译器已经支持自增。先运行完整程序，再按表格补充独立边界；不要将裸表达式片段直接作为编译单元输入。

### 9.1 合法完整程序：同时观察前置和后置

```c
int main() {
    int i = 3;
    int a = i++;
    int b = ++i;
    printf("%d %d %d\n", a, b, i);
    return 0;
}
```

| 阶段 | 实施后的预期 |
| --- | --- |
| `lexer.txt` | 两条 `INC ++`；前置为 `INC ++`、`IDENFR i`，后置次序相反 |
| `parser.txt` | 每个自增经 `<LVal>` 和 `<UnaryExp>`，不新增 `<IncExp>` / `<IncStmt>`；局部轨迹见第 5.3 节 |
| `error.txt` | 空 |
| `symbol.txt` | 内容如下，只包含声明，不打印自增后的变量值 |

```text
2 i Int
2 a Int
2 b Int
```

读懂这两个节点后再检查结果：`a` 的初值是后置自增返回的旧 i；`b` 的初值是前置自增返回的新 i。未来执行时，状态应按下表变化：

| 语句 | 自增表达式的结果 | 执行后 i | 接收变量 |
| --- | --- | --- | --- |
| `int i = 3;` | — | 3 | — |
| `int a = i++;` | 3 | 4 | a = 3 |
| `int b = ++i;` | 5 | 5 | b = 5 |

未来运行输出为 `3 5 5`，末尾换行。当前前端只能检查前后置 AST 标记及静态合法性，不能用符号表输出证明上述运行行为。

### 9.2 两个独立错误程序

常量目标错误：

```c
const int k = 1;
int main() {
    k++;
    return 0;
}
```

预期 `error.txt`：`3 h`。这里语法本身合法，错误来自目标不可修改。

常量上下文错误：

```c
int main() {
    int i = 1;
    const int n = ++i;
    return 0;
}
```

预期 `error.txt`：`3 o`。这里目标 i 可以修改，但该位置要求编译期常量。这两个程序分别验证两种约束，不要合成“对常量做自增”一个用例来代替。

### 9.3 边界与旧功能回归

表中的片段需放入匹配的声明 / 函数环境，错误用例各自独立，避免同一行错误被合并。

| 场景 | 片段 | 预期 |
| --- | --- | --- |
| 单个加号 | `i + 1` | 仍识别 `PLUS` |
| 前置、后置 | `++i; i++;` | 识别两个 `INC`；两个 AST 形态不同 |
| 最长匹配 | `i+++j`、`i + ++j`、`i + +j` | 分别为后置自增加 j、i 加前置自增、i 加普通单目正号 |
| 普通表达式输出回归 | `i + a[0]` | 原有 AST 层次与 watcher 输出不变 |
| 优先级 | `-i++`、`++i * 2`、`(i++) + 2` | 普通取负包住自增；自增作为乘加操作数；括号可包住结果 |
| 实参入口 | `f(++i)` | 正确识别首个实参；使用匹配的函数声明 |
| 返回入口 | `return ++i;` | 正确解析；函数返回类型与 `i` 一致 |
| 数组元素 | `a[k]++; ++a[k];` | 合法标量元素可修改 |
| 未定义目标 | `unknown++;` | `c` |
| 常量目标 | `const int c = 1; c++;` | `h` |
| 常量数组元素 | `const int a[1] = {1}; a[0]++;` | `h` |
| 整个数组 | `int a[2]; a++;` | `e` |
| 下标类型 | `int a[2]; char k = 'a'; a[k]++;` | 沿用现有下标必须为 `int` 的检查，报 `e` |
| 常量初值 | `int i = 1; const int n = ++i;` | 扩展错误 `o`，不能折叠出合法常量 |
| 数组长度 | `int i = 1; int a[++i];` | 扩展错误 `o` |
| 全局初值 | 全局可变 i 用作 `int n = i++;` 的初值 | 沿用当前全局初值的常量上下文，报 `o` |
| 非法目标 | `++1; (i)++; f()++;` | 本方案语法拒绝；当前框架不保证通用错误恢复 |
| 重复自增 | `++++i; i++++; ++i++;` | 本方案语法拒绝 |
| 普通单目限制 | `+ +i`、`- -i` | 保留已有相邻相同普通单目运算错误 `e` |
| 缺少分号 | 单独一行 `i++` 后接 `return 0;` | 保持缺分号错误 `i` 及原有恢复行为 |
| 文件截断 | 源码末尾只有 `++` 或 `i++` | 词法能结束；语法按缺目标 / 缺完整语句拒绝或恢复，不死循环 |
| 字符截断 | `char c = (char)255; char old = c++;` | 前端类型均为 char；未来 old 为 255，c 为 0 |
| int 溢出 | `int i = 2147483647; int x = ++i;` | 前端类型为 int；本扩展约定未来 i / x 均按 32 位环绕为最小 int |
| 副作用下标 | `a[i++]++` | 外层 target 的下标里再含一个 PostInc，不能复制下标节点求值 |
| 条件短路 | `if (0 && i++) ...`、`if (1 || ++i) ...` | 前端照常检查；未来被短路的自增不执行 |

运行时测试应另覆盖下标只求一次、短路右侧不执行；前端测试只验证结构和静态诊断。

实现后用项目现有的 `run.bat --build-only` 编译核心和 UI，再分词法、语法、语义阶段检查上述用例；回归原有单目运算、函数调用、强制转换、赋值与缺失括号恢复。

## 10. 使用已有测试生成器

`testgen/examples/inc.ebnf` 已包含新增候选式，`++ -> INC` 和自增的基本语义契约也已有支持。可以先独立生成参考数据：

```powershell
python -m testgen --rules testgen/examples/inc.ebnf --focus UnaryExp --suite mixed --count 30 --seed 42 --out build/inc-review
```

输出目录需为新目录或空目录。这里默认合并已有 `UnaryExp`，不要用只含两条自增规则的 `--replace` 删除普通表达式候选式。也可直接输入无 `// ` 前导的规则：

```text
UnaryExp -> '++' LVal | LVal '++'
```

生成器的参考输出不代表当前 Java 编译器已经实现这些规则。先按本文实施，再用 `--check` 或 `--check-only` 比较；同时检查 `case.json` 对非法语法形状采用的是阶段预期还是 `syntax-rejection`。测试生成器现有用法与覆盖边界详见[工具说明](../文法测试生成器.md)和[边界分析](../极端测试覆盖与官方样例分析.md)。

随机候选式覆盖不能代替第 9 节的定向验收，尤其需要单独验证普通表达式轨迹不变、三个枚举 switch 完整、`h/o` 分工，以及未来的单次求值与前后置结果。

## 11. 推荐实施顺序与漏改检查

1. 明确本文的语义约束及扩展错误码。
2. 增加 token 和词法分支，验证最长匹配与位置。
3. 按第 4 节扩展 `UnaryExp`，保留原有构造器 / 工厂，并增加自增工厂和 getter。
4. 按第 5 节替换两个 parser 方法，核对函数调用分支顺序、普通变量的 `<PrimaryExp>` 和赋值回溯。
5. 按第 6 节补齐 `analyzeUnaryExp()`、`analyzeInc()`、`lineOf()` 及错误枚举 / UI 说明。
6. 检查三个穷举 switch：`calculateConst()`、`analyzeUnaryExp()`、`lineOf()` 均覆盖 `PreInc/PostInc`，再编译并执行第 9 节前端验收。
7. 待后端存在后，落实写回、结果值、求值次数和短路语义。

不必新增 `IncStmt`、`IncExp`、符号类型或变量值更新逻辑，也不必给 `parseStmt()` 新增自增分支；`++` 保持独立于普通 `UnaryOp` 的两条候选式。
