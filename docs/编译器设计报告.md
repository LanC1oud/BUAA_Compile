## 一、参考编译器介绍

本次阅读的参考实现是北京航空航天大学 2024 级编译技术课程的一份完整 SysY 编译器：
[`swkfk/BUAA_SysY_Compiler_2024`](https://github.com/swkfk/BUAA_SysY_Compiler_2024)。
它用 Java 编写，共 164 个 Java 文件、约 1.25 万行代码，
完成 **SysY 源码 → LLVM IR → MIPS32 汇编** 的完整翻译，并附带一个规模可观的优化器。

### 1.1 总体结构

#### 1.1.1 流水线

编译器的入口是 `Compiler.java`，只调用 `Controller.run()`。
总调度`Controller`按阶段顺序执行，并在每个阶段结束后判断"当前作业阶段是否到此为止"：

```
Lexer.lex().emit()  ──►  TokenStream
Parser.parse().emit()  ──►  CompileUnit (AST)
Traverser.spawn()  ──►  SymbolTable（写入 Controller.symbols）+ ErrorTable
IrBuilder.build().emit()  ──►  IrModule (LLVM IR)
IrModule.runPass(...)  ──►  优化后的 IrModule
ArchModule.<一系列方法>()  ──►  MipsModule  ──►  mips.txt
```

`Controller` 中三个静态成员是全编译期共享的"全局状态"：

```java
public static final ErrorTable  errors  = new ErrorTable();   // 错误收集
public static final SymbolTable symbols = new SymbolTable();  // 语义分析产物
```

阶段之间的"截断"由 `HomeworkConfig.hw` 控制（`Lexer` / `Syntax` / `Semantic` / `CodegenI` / `CodegenII` …），
每个阶段结束后如果 `hw` 已经到了当前阶段，就把结果写进对应文件（`lexer.txt` / `parser.txt` / `symbol.txt` / …）
然后 `System.exit(0)` 退出。这样同一份代码可以在不同作业之间切换，而不需要维护多个分支。

#### 1.1.2 前端

- **词法分析**：`Lexer` 用 `PushbackReader` 逐字符读取，内部 `Reader` 嵌套类维护行号、列号与
  上一个字符的列号（用于 `unread('\n')` 时回退行号）。识别分派按首字符进行：
  字母/下划线 → 标识符（查关键字表）、数字 → 整数、`"` → 字符串、`'` → 字符、
  `/` → 注释或除号、其余 → 运算符。所有 token 存入 `TokenStream`。
- **语法分析**：`Parser` 是典型的递归下降，一个非终结符对应一个 `parseXxx()` 方法。
  它**不直接把输出写成字符串**，而是通过 `ParserWatcher.add(String)` 记录"Token 与语法成分的混合序列"，
  最后由 `ParserWatcher.toString()` 输出。这一层解耦使得"语法树构建"与"作业要求的输出格式"互不污染。
- **语义分析**：`Traverser` 遍历 `CompileUnit` 构建 `SymbolTable`，绑定 AST 结点上的符号引用，
  并报出错误 b ~ m（2024 文法，没有 `switch` 带来的错误码 `n`）。
- **AST**：`ASTNode` 是一层**极薄**的抽象基类（全文只有 `getName()` 与被它实现的 `toString()`），
  子类分为 `stmt` / `expr` / `decl` / `block` / `logical` / `misc` 等包，
  每个结点的 `toString()` 返回文法符号名（如 `<AddExp>`），从而实现"建树即输出"。
  结点本身**不保存源码位置**，位置信息只挂在 `Token` 上，需要时由
  `node.getToken().location()` 取——这一点对错误定位的写法影响很大。
- **分派方式**：整个前端**没有访问者模式**，也没有 `accept/visit` 双重分派。
  遍历是"手写递归 + `switch`/`instanceof`"，并且在语义分析（`frontend/Traverser`）与
  中间代码生成（`llvm/Traverser`）中**各写一套**。
  若干层级用"类 + 标签枚举"做联合体，而不是继承层次，例如
  `Stmt { enum Type {Assign, Expr, Block, If, For, …}; }`、
  `Decl { enum Type {Const, Variable}; Object declaration; }`、
  `BlockItem { enum Type {Decl, Stmt}; Object item; }`。
  作者在 `Conclusion.md` 中自评"变量与常量的声明有大量代码重复，显得十分冗余而易错"，指的正是这里。
- **表达式的"列表化"**：`ExprAdd{ ExprMul left; List<Op> ops; List<ExprMul> rights; }`
  把左递归文法折叠成"左操作数 + 运算符/右操作数列表"，既避免深层递归，也便于常量化简时一次性求和；
  `CondOr` / `CondAnd` / `CondEqu` / `CondRel` 采用同样的写法。

#### 1.1.3 中端 LLVM IR 与优化

中端没有把 IR 当字符串处理，而是完整实现了 LLVM 的**对象模型**：

- `Value`（一切可被使用的东西，自带名字与类型）→ `User`（能使用别人的东西）→
  `IBinary`/`ICall`/`IGep`/`ILoad`/`IStore`/`IPhi`/`ITerminator` 等指令，
  以及 `Function`、`BasicBlock`、`GlobalVariable`、常量 `ConstInteger`；
- `Use` 表示"某条指令用到了某个 Value"的边。这里有一个**已知的取舍**：`Use` 只挂在
  使用者自己的 `uses` 列表上，**没有反向的 use 链**（源码注释直言"这里的设计有点奇怪"），
  因此 `AggressiveDeadCodeEliminate` 只能靠全量扫描指令来寻找使用者，
  而不能像 LLVM 那样沿 use-def 链递归标记；
- `BasicBlock` 由指令序列组成，`IrModule` 是顶层容器，
  逐层下降 `toString()` 就是完整的 LLVM 文本（"对象即文本"，不需要先拼字符串再解析）；
- `IrBuilder` 提供插入指令的辅助方法，`llvm/Traverser` 负责从 AST 生成 IR。
  构建期上下文（`insertPoint`、`currentFunction`）集中在 builder 里。
  分支指令用"**可空的目标基本块 + 事后 `fillNullBlock` 回填**"解决前向引用，
  `break` / `continue` 的跳转目标正是用这种"先占位、后回填"的方式处理的。

几个通用容器也值得一提，它们是后面优化的地基：

| 容器 | 用途 |
| --- | --- |
| `DualLinkedList<T>` | 支持 O(1) 任意位置增删的双向链表，被 `BasicBlock.instructions`、`Function.blocks` 与全部 MIPS 列表使用；实现了 `Iterator.remove()`，使窥孔优化与死代码删除可以边遍历边删 |
| `Container<T>` | 可失效的懒缓存。`Function` 用它存 `cfg`/`dom`/`loopMap`/`loops`，IR 一旦被修改就 `invalidate()`，避免分析结果过期 |
| `Either<T,U>` | 二选一，用于 `SymbolVariable.constantValue`、全局变量初值、跳转指令的操作数 |
| `UndirectedGraph<T>` | 寄存器分配的冲突图 |
| `BackTrace` | 与前端共用的检查点回滚（`ErrorTable` 也实现了 `Traceable`） |

优化用 Pass 模式组织：抽象类 `llvm/Pass.java`，`IrModule.runPass(pass)` 逐个执行并返回 `this` 以支持链式调用。
仓库中可见的 Pass 分成两类：

- `analysises/`：只分析不修改——`AnalyseControlFlowGraph`（CFG）、`AnalyseDominatorTree`（支配树）、`AnalyseLoop`（循环信息）；
- `transforms/`：修改 IR——`MemoryToRegister`（Mem2Reg）、`AggressiveDeadCodeEliminate`（ADCE）、
  `ConstantFolding`、`MultiplySimplify`（乘法强度削弱）、`LoopHoist`（循环不变式外提）、
  `ControlFlowSimplify`（基本块合并）、`DeadBlockEliminate`、`ReadonlyGlobalEliminate`、
  `VariableRename`、`LocalVariableNumbering` 等。

`Controller` 中 pass 的**顺序**是作者反复调优的结果，且带有注释说明取舍，例如

```java
// LVN pass will make the temporary variable's lifetime longer, which will make the
// register allocation more difficult. ... When I shut down the LVN pass, the performance is better.
// .runPass(new LocalVariableNumbering())
```

`PerformanceRecord.md` 里逐 commit 记录 8 个测试点的成绩，可以看成"优化—性能"的对照实验。

#### 1.1.4 后端 MIPS

`arch/mips` 下按 LLVM 的层次再实现一遍目标机模型：`MipsModule` / `MipsBlock` / `MipsInstruction` /
`MipsOperand`（立即数、虚拟寄存器 `MipsVirtualRegister`、物理寄存器 `MipsPhysicalRegister`）。
`arch/mips/process` 里是代码生成的各个步骤（指令选择、Phi 指令移除、寄存器分配等，
见 `Optimize.md` 的 `MipsFunctionRegisterAllocate`、`MipsFunctionRemovePhi`），
`arch/mips/optimize` 里是与目标机强相关的优化（`Peephole` 窥孔优化）。

### 1.2 接口设计

参考编译器的接口呈现出明显的"**少量公开方法 + 链式调用 + 全局状态**"风格：

| 组件 | 公开接口 | 作用 |
| --- | --- | --- |
| `frontend.Lexer` | 构造方法、`lex()`、`emit()` | 读文件 → 词法分析 → 产出 `TokenStream` |
| `frontend.Parser` | 构造方法（需 `TokenStream` + `ParserWatcher`）、`parse()`、`emit()` | 产出 `CompileUnit` |
| `frontend.Traverser` | 构造方法（需 `CompileUnit`）、`spawn()` | 填充 `Controller.symbols`、`Controller.errors` |
| `llvm.IrBuilder` | 构造方法（需 `CompileUnit`）、`build()`、`emit()` | 产出 `IrModule` |
| `llvm.Pass` | 抽象类，`IrModule.runPass(pass)` 调用 | 分析与变形 IR |
| `arch.mips.process.MipsGenerator` | 生成 MIPS 代码的各阶段方法 | 产出 `MipsModule` |

几个关键的设计约定：

1. **`lex()` 与 `emit()` 分离**：`lex()` 只负责扫描并返回 `this`，`emit()` 负责"封口"（`freeze()`）
   并交付产物。`TokenStream.freeze()` 之后禁止再 `add()`，`next()/peek()` 之前则要求已 freeze，
   用一个布尔量把"建流期"和"消费期"两类误用都变成显式异常。
2. **`ParserWatcher` 作为观察者**：语法分析器不关心输出，所有输出通过 `add()` 转交。
3. **`BackTrace` 作为"检查点"**：`BackTrace.Traceable` 接口要求组件实现 `save()` / `restore(Object)`，
   `BackTrace(errors, tokens, watcher)` 一次性保存多个组件的状态，用于**试探性分析后的回滚**
   （例如区分 `Stmt -> LVal '=' Exp` 与 `Stmt -> [Exp] ';'`）。这在递归下降里是很轻量的回溯方案。
   `Parser` 的用法是 `try (BackTrace ignore = trace.save()) { parseLVal(); if (!among(Assign)) throw …; }`，
   配合 `ast/FirstSet.java`（只登记 `Expr` 与 `LeftValue` 两个 FIRST 集）先做快速筛除。
   `TokenStream.peek(int)` 支持**负偏移**，`Parser` 正是用 `peek(-1)` 取"刚消费的 token"来定位 i/j/k 类错误，
   本工程沿用了这一设计。
4. **错误码用枚举**：`ErrorType` 把 `b`/`c`/… 与语义名字绑定，`ErrorEntry` 负责输出 `行号 错误码`，
   `ErrorTable` 负责按行号排序输出，并实现 `Traceable` 以支持回滚时撤销错误记录。
5. **`utils/` 与 `helpers/` 分离**：`utils/` 放与编译原理无关的通用结构（`Pair`、`BackTrace`、
   `DualLinkedList`、`Either`、`UndirectedGraph`、`Container`），
   `helpers/` 放与编译相关但跨阶段的辅助（`ConstValue`、`LoopStorage`、`ParserWatcher`、
   `ArrayInitialString`、`Compatibility`、`GlobalCounter`、`Comments`）。

### 1.4 错误处理机制

1. **错误表可回滚**。`ErrorTable` 实现 `BackTrace.Traceable`，`save()` 返回当前长度，
   `restore()` 把超出部分的表项删掉。由于 `Parser` 的 `BackTrace` 同时管理
   `errors` / `tokens` / `watcher` 三个对象，一次 `restore()` 就能把"试探性解析"留下的
   **错误记录、token 游标、输出文本**全部撤销。
2. **分层上报**。词法层只对"`|`、`&` 未配对"调用 `errors.add(InvalidToken)`，
   其余（非法转义、字符常量缺失、数字前导零一类）用的是 `assert`——
   这意味着**生产运行时（未开 `-ea`）这些非法输入会被静默接受**，是本参考实现的一个明显弱点。
   语法层在 `Parser.consume()` 里捕获 `IllegalStateException`，只对 `;` `)` `]` 分别报 i/j/k 后继续；
   语义层是 b ~ h、l、m 的主要来源。
3. **错误优先的输出与恒为 0 的退出码**。每个阶段用
   `errors.noError() ? Configure.target : Configure.error` 决定写哪个文件；
   进入中端之前再统一判一次，所以有语法/语义错误时**不会生成 IR 与 MIPS**。
   但 `Controller.exit()` 里是无条件 `System.exit(0)`，
   **退出码不携带任何错误信息**，判题依赖 `error.txt` 的内容而非进程返回码。

## 二、编译器总体设计

### 2.1 总体结构

#### 2.1.1 数据结构

- **Token**（`record Token(TokenType type, String value, Navigation location)`）：
  类型、原始文本、源码位置。值为 `String`，数字/字符的**语义值在需要时现算**，
  避免词法阶段就要决定 `'a'` 该不该转义。
- **TokenStream**：`List<Token>` + 游标 + `frozen` 状态；提供 `peek(k)`、`among(...)`、
  `consume(...)`、`checkConsume(...)`；实现 `BackTrace.Traceable`，可以按游标回滚。
- **AST**：全部结点继承 `ASTNode`，`getName()` 返回文法符号名用于输出；
  按 `block / declaration / expression / function / statement` 分包。
- **符号表 Symbol 体系**：`Symbol`（名字、类型、是否全局、作用域号、`const` 限定符）
  → `SymbolVariable`（常量值、`static`、是否形参）/ `SymbolFunction`（返回类型、形参表）。
- **类型体系**：`SymbolType` → `Type`，`Type` 内部用 `Kind` 枚举区分 5 种类型
  （`int` / `char` / `int[]` / `char[]` / `void`）。
- **错误**：`ErrorType`（枚举，携带 a ~ n 的编码）、`ErrorEntry`（编码 + 位置）、
  `ErrorTable`（收集、排序输出、可回滚）。
- **配置**：`Configure`（输入输出路径、debug 开关）、`HomeworkConfig`（`Hw` 枚举 + 目标文件名）。

#### 2.1.2 编译过程

```
testfile.txt
   │  Lexer.lex().emit()                            （阶段一：词法分析）
   ▼
TokenStream ──────────────────────────► lexer.txt
   │  new Parser(tokens, watcher).parse().emit()    （阶段二：语法分析）
   ▼
CompileUnit(AST) ─────────────────────► parser.txt
   │  new Traverser(ast).spawn()                    （阶段三：语义分析）
   ▼
SymbolTable + ErrorTable ─────────────► symbol.txt / error.txt
   │  （阶段四：中间代码生成，待实现）
   ▼
   │  （阶段五：代码优化与目标代码生成，待实现）
   ▼
mips.txt / llvm_ir.txt
```

阶段之间的"截断"规则与参考实现一致：

```Java
if (HomeworkConfig.hw == HomeworkConfig.Hw.Semantic) {
    try (FileWriter writer = new FileWriter(errors.noError() ? Configure.target : Configure.error)) {
        writer.write((errors.noError() ? symbols.toString() : errors).toString());
    }
    Controller.exit();
}
```

`Controller` 另外提供两个全局对象：

```java
public static final ErrorTable  errors  = new ErrorTable();
public static final SymbolTable symbols = new SymbolTable();
```

把错误表与符号表放在控制中心，避免在 `Lexer`、`Parser`、`Traverser`
之间层层传参；各组件只持有引用，测试时也可以直接替换。`Configure.debug` 下的
`displayTokens` / `displayTokensWithAst` / `displaySymbols` / `displayErrors` 四个开关
用于把中间产物打到 `stderr`，不影响交付文件。

#### 2.1.3 错误处理

- 词法/语法/语义错误一律不抛异常中断，而是 `errors.add(type, navigation)` 后继续分析，
  以便一次报出全部错误。
- `ErrorTable.toString()` 按"行号 → 列号"排序后输出 `行号 错误码`，一行一条。
- 只要 `errors` 非空，就写 `error.txt` 且不再产出正常结果。
- 非法输入导致的 `IllegalStateException`（如 `consume` 遇到完全不该出现的 token）
  属于程序自身的 bug 直接抛出。

### 2.2 接口设计

## 三、词法分析设计

### 3.1 编码前的设计

#### 3.1.1 职责与边界

词法分析的输入是源文件路径，输出是一个已经封口的 `TokenStream`。
它负责：

- 跳过空白字符（空格、制表符、回车、换行、换页、垂直制表符）；
- 跳过 `//` 行注释与 `/* */` 块注释；
- 按 SysY 的词法规则切分出标识符/关键字、十进制整型常量、字符串常量、字符常量、运算符与界限符；
- 为每个 token 记录源码区间，供后续所有阶段的错误定位使用；
- 发现非法字符/非法转义时记录错误码 `a`，并继续扫描。

#### 3.1.2 结构设计

```
Lexer
├── static class Reader         字符级读取：行号 / 列号 / 回退
│     ├── read()                读一个字符并维护位置
│     ├── unread(int)           回退一个字符并恢复位置
│     └── location()            返回 Pair<行号, 列号>
├── lex()                       主循环：分派 + 收集
├── readIdentifier / readNumber / readString / readCharConst / readSlash / readOp
├── addToken(type, value, start) 统一封装位置区间（start, 当前 location()）
└── emit()                      冻结 TokenStream 并交付
```

字典式的查表放在 `frontend/token/` 下，与主流程分离：

- `Keywords.TABLE`：关键字 → `TokenType`（`Map<String, TokenType>`）；
- `Symbols.TABLE`：单字符界限符 → `TokenType`（`Map<Character, TokenType>`）；
- `Escapes.TABLE`：转义字符 → 实际字符（`Map<Character, Character>`）。

这样做的目的是把文法版本差异集中到三张小表里，便于后续增删文法。

#### 3.1.3 Token 的设计

```java
public record Token(TokenType type, String value, Navigation location) {
    public boolean is(TokenType type);
    public boolean among(TokenType... types);
    public String toString();        // 输出格式：TokenType + 空格 + value
    public String toDebugString();   // 调试格式
}
```

设计要点：

1. `TokenType` 的 `toString()` 直接返回作业要求的编码（如 `IntConst("INTCON")`），
   这样 `Token.toString()` 不需要任何 `switch`；
2. 字符串/字符常量在输出时要**还原转义**（`'\n'` 要打印成 `\n`），
   由 `Token.escapeValue()` 反向查 `Escapes.TABLE` 完成；
3. 值为 `String` 而不是 `Object`，需要数值的地方（`Number`、`case` 标签）现算，
   避免词法阶段承担语义决策。

#### 3.1.4 错误处理设计

- 只设计一种词法错误：`a`（非法 token）。
- 触发点：无法识别的字符、非法的转义序列、`|` 与 `&` 后面不是同名字符、
  字符串/字符常量未闭合。
- 报出位置后继续：不抛异常，不退出，保证一份有多个词法错误的文件能一次报全。

#### 3.1.5 输出格式

`TokenStream.toString()` 把每个 token 按扫描顺序输出一行：

```
CONSTTK const
INTTK int
IDENFR year
ASSIGN =
INTCON 2026
SEMICN ;
```

### 3.2 编码完成之后的修改

**修改记录由大模型根据git记录提供**

编码在两次提交中完成：`c38839a Lexer ver1`与 `dcc29a2 Lexer ver pass`。
与编码前的设计相比，架构没有变化，修改集中在"边界情况"与"与本文法的对齐"上，逐条如下。

#### 3.2.1 位置维护：EOF 被当成普通字符

首版 `Reader.read()`：

```java
int chr = reader.read();
if (chr == '\n') { lineno++; lastColumn = column; column = 0; }
else { column++; }        // ← EOF(-1) 也会把 column 加一
```

`read()` 返回 `-1` 表示文件结束，但它同样满足 `else` 分支，于是每调用一次就会把列号推进一格，
`unread(-1)` 又会把行号减一（`reader.unread('\n')` 分支），导致**文件末尾之后的位置信息整体错位**。
修改为显式短路：

```java
if (chr == -1) { return -1; }            // 位置不动
else if (chr == '\n') { … } else { column++; }
```

`unread(int)` 同样先判 `-1` 直接返回。这条修改的作用是：`error.txt` 的行号在任何输入下都可信。

#### 3.2.2 `readSlash()` 的前瞻错位

分派代码在调用 `readSlash()` 之前已经 `reader.unread(c)`，
即第一个 `/` 还留在回退缓冲里。而首版 `readSlash()` 开头直接 `c = reader.read();`，
读到的是那个 `/` 本身，于是：

- `// 注释`：第二个字符读到的是 `/`，恰好"碰巧正确"；
- `/* 块注释 */`：第二个字符读到的是 `/` 而不是 `*`，于是**块注释被当成行注释**，
  一直吃到行尾——后续整段代码被吞掉，是首版最隐蔽的一个 bug；
- `a / b`：读到的是 `/`，又被当成行注释，**除法运算符消失**。

修改：在 `readSlash()` 内部先显式消耗掉那个 `/`，再去读第二个字符，并写了注释说明原因：

```java
private void readSlash() throws IOException {
    Pair<Integer, Integer> start = reader.location();
    // The dispatch code leaves the first slash in the pushback reader.
    // Consume it before looking at the second character; otherwise
    // "/*" is mistaken for a line comment starting with the first '/'.
    reader.read();
    c = reader.read();
    …
}
```

#### 3.2.3 `|` 与 `&` 的单字符分支：错误码位置与"继续分析"

首版在读到单个 `|` 或 `&` 时"报错 + 回退 + 仍然发射 `||`/`&&`：

```java
if (c != '|') { errors.add(ErrorType.InvalidToken, location()); reader.unread(c); }
addToken(TokenType.Or, "||", start);
```

结果是 token 的值与类型不符，语法阶段继续分析这个`||`，错误会扩散成语法错误。
修改为：

```java
if (c != '|') {
    errors.add(ErrorType.InvalidToken, new Navigation(start, start));
    reader.unread(c);
    addToken(TokenType.Or, "|", start);
} else {
    addToken(TokenType.Or, "||", start);
}
```

#### 3.2.4 未知字符不再发射 `null` 类型的 token

首版：

```java
default -> addToken(Symbols.TABLE.get((char) c), String.valueOf((char) c), start);
```

`Symbols.TABLE` 未命中时返回 `null`，于是一个 `TokenType` 为 `null` 的 token 被塞进流里，
后面 `token.is(...)`、`token.toString()` 全部会炸。修改为：

```java
TokenType type = Symbols.TABLE.get((char) c);
if (type == null) { errors.add(ErrorType.InvalidToken, location()); }
else { addToken(type, String.valueOf((char) c), start); }
```

即"非法字符只报错、不产生 token"。

#### 3.3 大模型辅助生成代码的评价

词法分析阶段几乎未使用大模型，大部份架构设计依据参考编译器修改而成。仅在编码完成后的修改阶段进行bug核查，定位，以及测试数据生成。

由于项目体量尚且较小，大模型对“前瞻错位”类bug的核查定位及修改相当完美，批量生成的测试数据也帮助我自主定位了部分bug。

#### 3.4 对生成代码的人工修改

本阶段仅使用大模型解读参考编译器和定位bug，并未使用大模型生成正确代码。

## 四、语法分析设计

### 4.1 编码前的设计

#### 4.1.1 职责与边界

- 输入 `TokenStream`，输出 `CompileUnit`（语法树）。
- 按后序输出 token 与语法成分、
- 对 `;` `)` `]` 缺失做错误恢复并报出 i / j / k。

#### 4.1.2 文法到 AST 的映射

文法中每个有语义的子结点对应一个类；
只有一层包装、无附加信息的非终结符 （`Decl`、`BlockItem`、`BType`、`ForStmt`）不建独立结点，直接在父结点里表示：

| 文法 | AST 类 | 说明 |
| --- | --- | --- |
| `CompUnit` | `CompileUnit` | 声明列表 + 函数列表 + `mainFunc` |
| `Decl` | `Decl` 抽象类 | `ConstDecl` / `VarDecl` 两个子类 |
| `ConstInitVal` / `InitVal` | 同名类 | 内部用 `Kind {Exp, List, Str}` 区分三种形态 |
| `Block` / `BlockItem` | 同名类 | `BlockItem` 用 `Type {Decl, Stmt}` + `Object item` |
| `Stmt` 的 11 种形态 | `Stmt` 抽象 + 11 个子类 | 每个子类 `getName()` 都返回 `<Stmt>` |
| 表达式各层 | `Exp`/`AddExp`/`MulExp`/… | 二元层共用抽象基类 `BinaryExp`（左/中缀/右三元组） |
| `Cond` | `Cond` | 单独一层，把逻辑表达式与 `Exp` 区分开 |
| `UnaryExp` 的 4 种形态 | `UnaryExp` | 内部用 `Kind {Primary, Call, Unary, Cast}` + 静态工厂 |
| `PrimaryExp` 的 3 种形态 | `PrimaryExp` | 内部用 `Kind {Paren, LVal, Number}` |

#### 4.1.3 输出机制

`Parser` 不直接拼输出字符串，而是持有 `ParserWatcher`：

```java
public final class ParserWatcher implements BackTrace.Traceable {
    public void add(String line);
    public String toString();
    public Object save();  public void restore(Object state);   // 支持回滚
}
```

`Parser` 内部所有取 token 的动作都经过包装函数，包装函数在取 token 后记录：

```java
private Token consume(TokenType type) { … __watcher.add(token.toString()); … }
private boolean checkConsume(TokenType... types) { … __watcher.add(token.toString()); … }
private Token next() { … __watcher.add(String.valueOf(token)); … }
private <T> T watch(T inst) { __watcher.add(inst.toString()); return inst; }
```

token 在 `consume` 时被记录，非终结符在 `watch(new Xxx(...))`时被记录。
由于 `parseAddExp()` 先解析左边的 `MulExp` 再构造 `AddExp` 结点，
自然形成后序输出，与作业要求一致，无需额外遍历一遍树。

`ParserWatcher` 也实现 `Traceable`，是为了让试探性分析回滚时连输出一起撤销，防止回滚过的 token 多输出一遍。

#### 4.1.4 递归下降骨架

```
parse()                      CompUnit -> {Decl} {FuncDef} MainFuncDef
parseDecl()                  ConstDecl | VarDecl
parseConstDecl/Def/InitVal
parseVarDecl/Def/InitVal
parseFuncDef / parseMainFuncDef / parseFuncFParams / parseFuncFParam
parseBlock / parseBlockItem
parseStmt                    （按首 token 分派到 11 个分支）
parseExp / parseConstExp / parseCond
parseLOrExp → parseLAndExp → parseEqExp → parseRelExp → parseAddExp → parseMulExp
parseUnaryExp → parsePrimaryExp → parseLVal / parseNumber
```

文法左递归（`AddExp -> AddExp '+' MulExp`）统一用循环改写：

```java
AddExp exp = watch(new AddExp(parseMulExp()));
while (among(TokenType.Plus, TokenType.Minus)) {
    Token op = consumeAny(TokenType.Plus, TokenType.Minus);
    exp = watch(new AddExp(exp, op, parseMulExp()));
}
return exp;
```

循环改写使树向左生长（`a+b+c` → `AddExp(AddExp(a,+,b),+,c)`），保持了左结合语义。

#### 4.1.5 两处歧义的处理设计

**(1) `CompUnit` 顶层的 `int/char` 开头**

`int`/`char` 开头可能是三种东西：变量声明、函数定义、`main` 函数定义。
用固定 1~2 个 token 的前瞻解决，不需要回溯：

```java
if (among(TokenType.Int, TokenType.Char)) {
    if (among(1, TokenType.Main)) {                                     // int main
        ast.setMainFunc(parseMainFuncDef());
    } else if (among(1, TokenType.Ident) && among(2, TokenType.LParen)) { // int f(
        ast.addFunction(parseFuncDef());
    } else {
        ast.addDeclaration(parseDecl());                                 // int x …
    }
}
```

**(2) `Stmt -> LVal '=' Exp ';'` 与 `Stmt -> [Exp] ';'`**

两者都以 `Ident` 开头，只能"试着解析完左值再看下一个是不是 `=`"。
设计上用 `BackTrace` 做**带副作用的回滚**：

```java
private boolean isAssignStmt() {
    if (!among(TokenType.Ident)) return false;
    trace.save();
    boolean assign = false;
    try {
        parseLVal();                       // 试探性解析
        assign = among(TokenType.Assign);
    } catch (RuntimeException e) {
        assign = false;
    } finally {
        trace.restore();                   // token 游标、输出、错误 三者一起回滚
    }
    return assign;
}
```

### 4.2 编码完成之后的修改

**修改记录由大模型根据git记录提供**

编码在 `dc43d25`（一次提交 56 个文件、2200+ 行）中完成，随后 `c388dc3` 做了小修。
总体而言，设计中的骨架全部保留（递归下降、观察者输出、`BackTrace` 回滚、`consume` 恢复），
修改集中在"基础设施的健壮性"与"与本文法的对齐"上。

#### 4.2.1 `TokenStream` 的越界与 EOF 处理

- `among(TokenType... types)` 首版直接 `peek().among(types)`，
  在文件末尾（`peek()` 返回 `null`）会 NPE。改为：

  ```java
  Token token = peek();
  return token != null && token.among(types);
  ```

#### 4.2.2 `Token` 从普通类改为 `record`

```java
public record Token(TokenType type, String value, Navigation location) { … }
```

#### 4.2.3 `ErrorTable` 变为可回滚，并明确排序规则

`ErrorTable` 增加 `Traceable` 实现：

```java
@Override public Object save() { return errors.size(); }
@Override public void restore(Object state) { while (errors.size() > (int) state) errors.remove(errors.size() - 1); }
```

修改前 `isAssignStmt()` 的试探解析就会把"试探过程中产生的错误"留在表里，
出现"合法程序报错"的假阳性。同时把排序从参考实现的
`Comparator.comparingInt(t0 -> Integer.parseInt(t0.toString().split(" ")[0]))`
改为显式的 `comparingInt(ErrorEntry::getLine).thenComparingInt(ErrorEntry::getColumn)`：
不再依赖字符串切分，且同行错误按列号稳定排序。

#### 4.2.4 细节修正

- `parseBlock()` 的循环条件由 `while (!among(RBrace))` 改为
  `while (!among(RBrace) && !eof())`：缺 `}` 时不会死循环（会一路推进到 EOF 后结束），
  避免输入不完整导致编译器挂死。
- `parseCaseStmt()` 的内部语句循环加上 `!eof()` 与 `Case/Default/RBrace` 三个终止条件，
  保证 `switch` 里语句能正确地绑定到当前 case 上。

#### 4.2.8 显式类型转换的判定

文法 `UnaryExp -> '(' BType ')' UnaryExp` 与 `PrimaryExp -> '(' Exp ')'` 都以 `(` 开头，
用"第二个 token 是不是类型关键字"这一前瞻即可区分，无需回溯：

```java
if (among(TokenType.LParen) && among(1, TokenType.Int, TokenType.Char)) {
    consume(TokenType.LParen);
    Token castType = parseBType();
    consume(TokenType.RParen);       // 缺 ')' 时报 j，位置在 BType 上（与文档要求一致）
    return watch(UnaryExp.cast(castType, parseUnaryExp()));
}
```

#### 4.2.9 `CompileUnit` 中 `mainFunc` 的存法

`CompileUnit` 里用一个长度为 1 的数组保存 `main`：

```java
private final MainFuncDef[] mainFunc = new MainFuncDef[1];
```

原因是 `main` 只有一个，但"在解析过程中回填"需要一个可变的引用容器；
用数组是 Java 里最轻量的做法，且不需要为 `CompileUnit` 增加 setter 的可见性问题。

输入 `CompileUnit`，输出：

- **符号表**（`Controller.symbols`）：全局 + 各作用域的符号，附带作用域号，可直接输出为 `symbol.txt`；
- **错误表**（`Controller.errors`）：错误码 b ~ n；
- **AST 上的绑定信息**：`LVal` 结点绑定到 `SymbolVariable`，供后续阶段使用。

#### 5.1.2 符号表设计

**作用域模型**：符号表是一个作用域栈，栈底是全局作用域（编号 1）。
进入一个块 / 函数体就 `newScope()`，离开就 `exitScope()`。
查找变量时从栈顶向栈底逐层查找，内层优先。

**作用域编号规则**：编号按进入顺序递增，而不是按嵌套深度。
唯一的编号来源是一个静态计数器：

```java
private static int counter = 1;                 // 全局作用域 = 1
public void newScope() { counter++; stack.push(new HashMap<>()); stackOfScopeId.push(counter); }
```

**形参与函数体最外层共用作用域号**。

**符号输出顺序**：`Symbol` 实现 `Comparable`，先按作用域号降序、同作用域内按声明顺序升序：

```java
if (symbolTableIndex == symbol.symbolTableIndex) return Integer.compare(index, symbol.index);
return Integer.compare(symbolTableIndex, symbol.symbolTableIndex);
```

#### 5.1.3 类型系统设计

只需要区分 5 种类型：`int`、`char`、`int[]`、`char[]`、`void`。
设计为**5 个单例 + 数组按长度新建**：

```java
public static final Type Int, Char, Void, IntArray, CharArray;   // 单例
private final Kind kind;          // Int/Char/IntArray/CharArray/Void
private final Type elementType;   // 数组元素类型
private final int length;         // 数组长度；0 = 长度未知（形参 int a[]）
```

`length == 0` 同时承担"空"和"未知"两种含义。

**类型比较规则**：

- 标量：严格相等，`int` 与 `char` 不允许隐式混用；
- 数组：元素类型相同即可互相传递，长度不参与比较（`int t[5]` 可以传给 `int x[]`）：

```java
public boolean isPassableTo(Type parameter) {
    if (this == parameter) return true;
    if (!isArray() || !parameter.isArray()) return false;
    return elementType == parameter.elementType;
}
```

因此 `equals()` 对数组比较 `kind + length`，而可传递性用单独的 `isPassableTo()` 表达，
两个语义分开，避免把"同一类型"和"可兼容"混为一谈。

**符号表输出用的类型名**：`Const` / `Static` 是符号的属性而不是类型的属性，
所以由符号把自己的修饰位传给类型：

```java
abstract public String displayName(boolean isConst, boolean isStatic);
// Int / Char / IntArray / CharArray / Void
// ConstInt / ConstIntArray / StaticInt / StaticIntArray / IntFunc / VoidFunc
```

#### 5.1.4 常量表达式求值与常量折叠

常量需要用在四个地方：数组长度、`const` 变量的初值、`case` 标签、全局/`static` 变量的初值。
设计上把求值能力挂在 AST 结点上：

```java
// ASTNode 默认实现：不是表达式结点就没有值
public int calculateConst() { throw new UnsupportedOperationException(getName() + " 无法作为常量求值"); }

// 表达式结点覆写：
//   Number      → 字面量值（十进制整型 / 字符码位）
//   LVal        → 查符号上保存的常量值（标量）或常量数组元素（数组 + 常量下标）
//   PrimaryExp  → 按 Kind 转发（括号分支转发到 Exp，见下）
//   UnaryExp    → 一元运算 / 显式类型转换；函数调用没有编译期值
//   BinaryExp   → 先递归左、再按本层 (op, right) 折叠（保持左结合）
//   Exp/ConstExp→ 转发到 AddExp
```

`Exp` 这一层的转发是必需的：`PrimaryExp` 的括号分支里装的是 `Exp` 而不是 `ConstExp`，
没有它就无法折叠 `(1 + 2) * 3`。

二元运算的求值集中在一个工具类里，避免六层表达式各写一份 `switch`：

```java
public static int calculate(int left, int right, TokenType op);   // utils/ConstValue
```

错误语义上区分两类情况：

- 算术异常（除 0、模 0）→ 抛 `ArithmeticException`；
- 非编译期常量（变量非常量、函数调用、符号未解析）→ 抛 `UnsupportedOperationException`。

调用方需要用"能不能折出来"来决定后续动作，所以再包一层安全入口：

```java
public static Integer fold(ASTNode node) {          // utils/ConstFolder
    try { return node.calculateConst(); } catch (RuntimeException e) { return null; }
}
```

即"异常 → `null`"，用返回值而不是异常控制流程。

#### 5.1.5 遍历策略

```
spawn()
├── 先分析全部全局声明          ← 让全局名字（含前向引用）在所有函数体里可见
├── 再逐个 FuncDef
└── 最后 MainFuncDef
```

先全部全局声明、再函数体，是为了支持函数体里引用在其后声明的全局变量。
每个 `FuncDef` 的处理顺序：`addFunction` → `newScope` → 注册形参 → 分析函数体 → `exitScope`。

`Traverser` 需要维护的上下文状态：

| 状态 | 用途 |
| --- | --- |
| `returnTypeIsVoid` | `void` 函数里出现带值 `return` → 错误 f |
| `currentFunctionType` | 返回值的类型检查 → 错误 e |
| `returnWithValueFound` | 是否出现过带值 `return` → 错误 g |
| `loopDepth` | `continue` 合法性 → 错误 m |
| `breakDepth` | `break` 合法性（循环 **或** `switch`）→ 错误 m |
| `Map<ASTNode, Type> types` | 每个表达式的类型缓存（`IdentityHashMap`，按结点身份） |

**m 需要两个深度**：`break` 在循环或 `switch` 里都合法，`continue` 只在循环里合法，
用一个 `loopDepth` 表达不了，所以拆成 `loopDepth` 与 `breakDepth`，
`switch` 只递增 `breakDepth`，`while` 两者都递增。

#### 5.1.6 需要报出的错误（b ~ n）与判据设计

| 码 | 含义 | 判据 |
| --- | --- | --- |
| b | 名字重定义 | 当前作用域已有同名，或是保留标识符（变量、函数、形参各自判断） |
| c | 未定义引用 | 左值名在符号表中查不到；被调用名不是函数（含"把变量当函数调用"） |
| d | 参数个数不符 | 实参个数 ≠ 形参个数 |
| e | 类型不匹配 | 二元/一元运算的操作数、赋值左右、数组下标、返回值、实参、`case` 值、字符串初始化长度 |
| f | `void` 函数不应有返回值 | `returnTypeIsVoid && stmt.hasExp()` |
| g | 非 `void` 函数缺少返回语句 | 函数体**末尾**不是带值 `return`（不做控制流分析） |
| h | 向常量赋值 | 左值绑定的符号 `isConst()` |
| i/j/k | 缺少 `;` / `)` / `]` | 语法阶段已报，语义阶段不再涉及 |
| l | `printf` 格式符与实参个数不符 | 扫描格式串中的 `%`，`%%` 不计数 |
| m | 非法循环控制 | `break` 时 `breakDepth == 0`；`continue` 时 `loopDepth == 0` |
| n | `switch` 中 `case`/`default` 重复 | `case` 常量值集合查重 + 是否出现第二个 `default` |

任何一条检查失败后，仍要让后续分析尽可能继续。例如
错误 b 之后照常分析函数体（用一个临时符号兜底），否则函数体里的其它错误会全部漏报；
错误 d 之后不再查类型，避免同一处调用点连报两个错。


每行是 `作用域号 名字 类型名`，按 5.1.2 的排序规则输出。

### 5.2 编码完成之后的修改

**修改记录由大模型根据git记录提供**

语义阶段分三次提交完成：`5a88914 Semantic ver1`（搭建符号表 / 类型 / 常量求值）、
`c2d7ec8 semantic ver complete`（补齐 `Traverser` 全部检查，单次提交 875 行）、
`8eeb0a0` / `88b2ac8`（收尾修正）。
架构与设计一致（作用域栈 + 类型单例 + AST 上挂常量求值 + 单趟遍历），
修改集中在**类型表示、作用域编号、错误覆盖范围**这三处。

#### 5.2.1 类型系统：从"按位宽区分"改为"按种类区分"（最本质的一处修改）

参考实现沿用了 LLVM 的思路，用位宽区分类型：`I8` 表示 `char`，`I32` 表示 `int`，
并且 `TypeInt(8).is("int")` 返回 `true`，于是 `int` 与 `char` 被归为同一类，
`compatible()` 里"两者都是 int 就兼容"这条规则得以成立。

本文法明确要求 `int` 与 `char` 是两种不同类型、**不允许隐式混用**，
所以 `Type` 改为按 `Kind` 枚举判断身份，并删除宽度概念：

```java
public enum Kind { Int("int","Int"), Char("char","Char"), IntArray("int[]","Int"), CharArray("char[]","Char"), Void("void","Void"); }
```

`is(String)` 只认 `"int"` / `"char"` / `"int[]"` / `"char[]"` / `"void"` 五个名字，
**刻意不接受 `i32` / `i8` 这类宽度别名**，否则 `int` 与 `char` 又会被混为一谈。
`SymbolType` 上的 `compatible()` 一并删除，类型比较统一用 `Type.equals()`，
只有"数组实参 → 数组形参"这一处走 `isPassableTo()`。

#### 5.2.2 类型名的拼装方式重构

首版给了 `Kind.baseName()`，用"去掉 `Array` 后缀"的字符串操作反推词根，再由调用方拼前缀。
问题有三：字符串裁剪脆弱、`Array` 后缀的归属不清（到底属于类型还是调用方）、
`Void` 也会被拼成 `ConstVoid`。

修改后把词根与后缀都放进 `Kind`，由静态方法一次拼好：

```java
public static String displayName(Kind kind, boolean isConst, boolean isStatic, boolean isArray) {
    String prefix = isConst ? "Const" : (isStatic ? "Static" : "");
    return prefix + kind.displayName + (isArray ? "Array" : "");
}
```

`IntArray` / `CharArray` 的 `displayName` 从 `"IntArray"` 改为 `"Int"`（后缀由参数补），
这样数组类型和非数组类型共用同一个方法，且 `Const` 与 `Static` 互斥的语义在代码里显式表达。

#### 5.2.3 作用域编号：从"按深度"改为"按进入顺序"

首版照抄参考实现，编号与栈深度耦合。实际用官方样例验证时发现：
`getDay` / `fun` / `main` 的函数体应当是 2、3、4，`main` 里的嵌套块应当是 5。
按深度编号的话嵌套块只会得到 3。修改后用一个静态计数器按进入顺序发号，
并在 `SymbolTable` 的类注释里把这个反例写清楚，避免以后又被"看起来更自然的深度编号"改回去。

同一次修改还把 `addVariable()` 里的"自动开新作用域"去掉：

```java
// 首版：addVariable 内部顺手 newScope()，形参和函数体因此分属两个作用域号
// 现在：由 Traverser 在进入函数时只开一次作用域，形参与函数体最外层共用编号
```

#### 5.2.4 运行时库函数：可查但不进输出

首版把 `printf` / `getint` / `getchar` 作为特例写死在一个 `bumpKeepIdentifier()` 里，
只能判断"不能被重定义"，**不能查类型**，因此调用它们时无法检查参数。
本文法的库函数有 7 个且带参数信息（`get_string(char s[], int n)`、`put_char(char)` …），
修改为在构造时统一预注册：

```java
private void installRuntimeFunctions() {
    library("get_int", Type.Int);
    library("get_char", Type.Int);
    library("get_string", Type.Int, Type.CharArray, Type.Int);
    library("put_int", Type.Void, Type.Int);
    library("put_char", Type.Void, Type.Char);
    library("put_string", Type.Void, Type.CharArray);
    library("printf", Type.Void, Type.CharArray);
}
```

它们进 `allFunctions`（能查、能检查实参）但**不进 `outputList`**（不出现在 symbol.txt）。
`RESERVED` 集合加入这 7 个名字与 `main`，供"重定义"判断使用。

#### 5.2.5 `main` 也不允许被重定义

首版只防了库函数名。本文法中 `main` 是关键字，用户不可能再定义名为 `main` 的函数，
但可以被"定义名为 `main` 的变量"之类操作绕过，所以把 `main` 也加入 `RESERVED`。
同时明确 `main` **不进符号表**（它是关键字，不是用户符号），
由 `analyzeMainFuncDef()` 单独处理函数体与错误 g。

#### 5.2.6 常量折叠：从"异常满天飞"到统一入口

首版让各处直接调 `calculateConst()`，于是每一处调用点都要写 `try/catch` 处理
"不是常量"的情况，代码里到处是异常处理，可读性差。
修改为新增 `utils/ConstFolder`：

```java
public static Integer fold(ASTNode node) {
    if (node == null) return null;
    try { return node.calculateConst(); } catch (RuntimeException e) { return null; }
}
```

调用方从此只写 `Integer size = ConstFolder.fold(length); if (size == null) { … }`。
新节点 `FixedArray` 承担常量数组的求值：

- `FixedArray.from(int length, ConstInitVal init)` 与 `from(int length, InitVal init)` 两个重载，
  分别对应 `const` 与普通变量的初始化列表；
- 字符串初始化单独走 `fromString()`，把字符逐个放入并在末尾补 `'\0'`；
- 超出数组长度的元素被丢弃（长度由语法保证合法，语义阶段只做对齐）；
- `get(int)` 对越界下标抛 `IndexOutOfBoundsException`，使"常量下标越界"能被 `ConstFolder`
  捕获成"折不出来"，而不会悄悄给出错误值。

`LVal.calculateConst()` 因此扩展为支持常量数组元素：先看符号有没有 `getConstantArray()`，
有则要求下标本身可折叠，再去元素表里查。

#### 5.2.7 错误 e 的覆盖面从 3 类扩到 7 类

参考实现的 `MismatchedParameterType` 只出现在三处（多类型混合运算、返回值、实参）。
本文法要求 `e` 覆盖更多场景，编码后逐一补齐：

1. 二元运算两个操作数类型不同（含数组/`void` 参与运算）；
2. 一元运算的操作数不是基本类型；
3. 赋值左右类型不符（报在**左值所在行**）；
4. 返回值类型与函数返回类型不符；
5. 函数实参与形参类型不符（每个调用点最多报一次，`break` 掉后续参数）；
6. `case` 标签类型与 `switch` 表达式类型不符；
7. 数组下标不是 `int`、对非数组做下标访问、初始化列表元素个数超长、
   字符串初始化长度超出数组容量。

为了不让同一处表达式重复报错，引入"**同一结点只报一次**"的收敛策略：
每个表达式结点的类型结果都放进 `types` 缓存，重复访问直接命中缓存；
`checkSameType()` 只在真正比较时报警，`analyzeCall()` 检查到第一个不匹配的实参就 `break`。

#### 5.2.8 错误 m：一个 `loopDepth` 拆成两个

首版只有 `loopDepth`，于是 `switch` 里的 `break` 会被误报为非法。
修改为 `loopDepth`（`continue` 用）与 `breakDepth`（`break` 用）：

```java
} else if (stmt instanceof WhileStmt whileStmt) {
    analyzeCond(whileStmt.getCond());
    loopDepth++; breakDepth++;              // 循环：两者都进
    visitStmt(whileStmt.getBody());
    loopDepth--; breakDepth--;
} else if (stmt instanceof SwitchStmt switchStmt) {
    analyzeSwitch(switchStmt);              // switch 内部只递增 breakDepth
}
```

`analyzeSwitch()` 用 `try/finally` 保证 `breakDepth` 一定还原，避免异常路径下状态泄漏。

#### 5.2.9 错误 n：新增 `case` 判重

这是参考实现里**完全缺失**的错误（2024 没有 `switch`）。实现为：

```java
Set<Integer> usedLabels = new HashSet<>();
boolean defaultSeen = false;
for (CaseStmt caseStmt : stmt.getCases()) {
    if (caseStmt.isDefault()) {
        if (defaultSeen) errors.add(ErrorType.DuplicatedCaseLabel, caseStmt.getKeyword().location());
        defaultSeen = true;
    } else {
        Integer value = ConstFolder.fold(caseStmt.getNumber());
        if (value != null && !usedLabels.add(value)) {
            errors.add(ErrorType.DuplicatedCaseLabel, caseStmt.getNumber().getToken().location());
        }
        …类型检查…
    }
    for (Stmt body : caseStmt.getStmts()) visitStmt(body);
}
```

两个细节来自实际调试：

1. 首版把 `case` 分支写成 `if (caseStmt.isDefault()) { … } else { … }`，
   而在处理 `default` 时用 `continue` 跳过了后续语句，导致 **`default` 之后的 case 体不被分析**，
   `default` 分支里的未定义引用、类型错误全部漏报。改为"判重与类型检查用 if/else，
   语句分析统一放在后面"的结构。
2. `default` 的重置必须在**每次进入 `switch` 时**做（`defaultSeen = false`），
   否则嵌套或连续的 `switch` 会互相干扰。

#### 5.2.10 错误 g：只看函数体末尾

官方要求是"非 `void` 函数**最后**应有返回值"，不做控制流可达性分析。
实现为 `checkMissingReturn(body, isVoid)`：若 `isVoid` 或曾经出现过带值 `return` 就直接返回，
否则报在块结束 token（`}`）的位置。

需要注意它与错误 f 的分工：

- `void` 函数里出现 `return exp;` → **f**；
- 非 `void` 函数里出现 `return;`（不带值）→ 也计入"遇到过 return"，但最终由 **g** 兜住；
- 非 `void` 函数完全没有 `return` → 只在 `}` 处报一次 **g**。

首版把"出现过 `return`"当成"出现过带值 `return`"，导致 `int f() { return; }` 不报 g，
修正后把标志位的语义收窄为 `returnWithValueFound`。

#### 5.2.11 错误位置的兜底与修正

- `analyzeAssign` 的类型错误要求报在**左值所在行**，因此引入 `lineOf(ASTNode)`，
  按结点类型回溯到具体 `Token`（`LVal` → 标识符、`Number` → 字面量、`BinaryExp` → 运算符、
  `UnaryExp` → 调用名/转换类型、`PrimaryExp` → 递归）。
- 初始化列表没有自己的 `Token`，`initTokenLine()` 借用第一个元素的记号位置；
- 实在定位不到时用常量 `DeclarationFallback`（第 0 行），既不会与真实行号冲突，
  也让"位置缺失"在输出里显眼可见。

#### 5.2.12 显式类型转换的求值语义：有符号 → 无符号

首版沿用 C 的 `(byte) value`（有符号窄化）：

```java
if (castType.is(TokenType.Char)) return (byte) value;   // (char)255 → -1
```

本文法中 `char` 是 **unsigned char**（0~255，溢出模 256），
`(char)255` 应当得到 `255`。修改为：

```java
if (castType.is(TokenType.Char)) return value & 0xFF;   // (char)255 → 255
```

代码注释里明确写了"参考实现按有符号处理，这里必须改"，避免以后被"优化"回去。

#### 5.2.13 数组相关的补充检查

首版只检查"名字未定义"。编码后按本文法补上：

- 数组长度必须是**能折出来的正整数**，折不出来时退化为"长度未知的数组"，
  **只影响后续下标检查的精度，不再额外报错**（语法阶段已保证该位置是 `ConstExp`）；
- 数组下标必须是 `int`（`char` 作下标 → 错误 e）；
- 不能对非数组做下标访问（→ 错误 e）；
- 形参类型 `int a[]` 映射为"长度未知的数组"（`Type.ofArray(base, 0)`），
  从而让 `int t[5]` 实参通过 `isPassableTo()` 检查。

#### 5.2.14 `printf` 格式符计数

```java
for (int i = 0; i < text.length(); i++) {
    if (text.charAt(i) != '%') continue;
    i++;
    if (i >= text.length()) break;
    if (text.charAt(i) == '%') continue;   // %% 不消耗实参
    count++;
}
```

依赖一个前提：**转义在词法阶段就已解码**，所以格式串里不会再有 `\n` 之类的两字符序列干扰计数；
`%%` 通过"多看一个字符"排除。
