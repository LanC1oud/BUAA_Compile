# 文法扩展示例集

这些文档根据当前仓库的 Java 前端编写，提供可供实施的修改方案和关键代码，**不表示对应功能已经实现**。本次整理只修改文档，没有修改编译器或测试生成器。路径表中的文件名相对于项目根目录。

## 1. 示例导航

| 示例 | 主要学习点 | 核心方法 / 结构 |
| --- | --- | --- |
| [自增运算符 `++`](文法扩展-自增运算符++.md) | 前后置表达式、可修改左值、副作用、常量上下文 | `parseUnaryExp()`、`analyzeInc()` |
| [按位取反 `~`](文法扩展-按位取反.md) | 复用既有单目表达式、表达式起始集合、字符截断 | `atExpressionStart()`、`analyzeUnaryOp()`、`calculateUnary()` |
| [幂运算 `**`](文法扩展-幂运算符.md) | 插入优先级层、结合性、AST 递归、常量求值、定义域 | `PowerExp`、`parsePowerExp()`、`analyzePowerExp()`、`powInt32()` |
| [复合赋值 `+=`](文法扩展-复合赋值.md) | 赋值语句判别与回溯、类型一致、左值只求值一次 | `CompoundAssignStmt`、`isAssignStmt()`、`analyzeCompoundAssign()` |
| [`do…while` 循环](文法扩展-do-while循环.md) | 新关键字、新语句、循环上下文、作用域、跳转目标 | `DoWhileStmt`、`parseDoWhileStmt()`、`analyzeDoWhile()` |

建议按 `~` → `**` → `+=` → `do…while` → `++` 阅读。每份方案可独立实施；相互组合时按第 3 节合并共同改动。

## 2. 共同约定

- 这些是本项目自定义的扩展规则，不属于官方可见样例已经验证的课程规则。尤其要先确认操作数类型、结合性、常量上下文和错误码，再复制实现。
- 文法输入不带 `// ` 前导。终结符加引号，例如 `Stmt -> LVal '+=' Exp ';'`。
- 当前工程实现词法、语法和语义分析。文档中的运行结果用于定义语义及指导未来后端测试；当前阶段验收 `lexer.txt`、`parser.txt`、`symbol.txt`、`error.txt`。
- 沿用项目的严格基本类型规则：通常 `int` 与 `char` 不隐式混算，字符结果按 `& 0xFF` 截断。不要直接套用 C 的整型提升规则。
- `watch()` 的调用位置决定语法输出。新增表达式层可能改变旧程序的 `parser.txt`；新增 `Stmt` 子类仍输出 `<Stmt>`。
- 关键代码中展示的类应保存到对应文件，方法应放进表格指定的现有类；保留未展示的现有分支和所需 import。多份方案改同一方法时合并分支，不能整段覆盖其它扩展。
- 非法语法形状没有课程统一错误码时，验收“解析拒绝并能结束”，不编造 `error.txt`。已有 `i/j/k` 恢复仍按上一 token 的行号定位。

## 3. 同时实现时的合并点

| 共同位置 | 合并要求 |
| --- | --- |
| `Lexer.readOp()` 的 `case '+'` | 同时支持 `++`、`+=`、`+`，只写一个分支，先读取第二个字符后判别 |
| `Parser.atExpressionStart()` | 在原集合中同时加入前置 `Inc` 与 `Tilde`；`Power`、`PlusAssign`、`Do` 都不是表达式起始符 |
| `Parser.parseUnaryExp()` | 合并自增分支和含 `Tilde` 的普通单目分支，保留类型转换、函数调用和主表达式 |
| `Parser.parseStmt()` / `Traverser.visitStmt()` | 分别加入复合赋值及后测试循环，保留原有赋值、while、switch 等分支 |
| `Traverser.analyzeOperand()` | 新增 `PowerExp` 分派；`~` 仍由 `UnaryExp` 的已有分派处理 |
| `ErrorType` / `DisplayError` | 自增方案预留扩展错误 `o`，幂方案预留扩展错误 `p`；二者都不是官方错误码 |
| 测试生成器 | 同步合并文法、token 名、语义模型和定向边界，不直接把新语法当成已有语法的同义写法 |

词法采用最长匹配：同时启用 `++` 和 `+=` 时，`++=` 应切成 `INC ++`、`ASSIGN =`；`+ +=` 应切成 `PLUS +`、`PLUSEQ +=`。字符串和注释内部不按这些运算符切分。

幂方案增加 `<PowerExp>` 输出层。测试生成器已有同名演示文法；实施 Java 方案时仍需同步文档中定义的负指数诊断，不能只复用其类型配置就视为完整支持。

## 4. 每次扩展的最低验收

1. 先测单个新 token，再测其前后相邻的旧 token、空白、注释和文件末尾。
2. 用小程序锁定 AST 结构、优先级、结合性和语法输出，再测常量、变量、数组元素、函数实参和条件位置。
3. 分开测试未定义名称、类型错误、常量修改及 `i/j/k` 恢复；同一行的多个错误还需按 `ErrorTable` 的优先级验证。
4. 每项至少保留一个合法完整程序、一个独立错误用例、一个与旧文法交互的用例；再加入深嵌套和长链压力测试。
5. 运行旧基础边界与官方可见样例回归。出现新增 AST 输出层时先更新输出契约，不能把所有差异直接判为错误。

用例数量、顶层候选式覆盖率都不能证明语言完备。各文档列出的边界是测试设计起点，组合后的副作用、深度和路径仍需继续扩充。
