# 文法增添通用指南

本文给出可复用的文法扩展方法，并对应到当前 SysY 项目的文件与方法。适用于新增运算符、表达式、语句、声明、类型及函数规则。本文仅提供指导与代码示意，不代表这些功能已在编译器中实现。

一个扩展需要同时说明：**如何写、如何解析、是否合法、如何求值、如何验证**。BNF/EBNF 主要描述结构，不能单独决定类型规则、作用域、错误码或运行时行为。

当前项目已实现词法、语法、语义分析；IR 和目标代码生成尚未实现。因此前端验收与未来运行时验收应分别记录。

## 1. 每次扩展先填写一张规则说明表

在写代码前，用下面的表把新功能定义清楚。与该功能无关的项标为“不适用”。

| 项目 | 需要确定的内容 |
| --- | --- |
| 扩展目标 | 新运算符、新表达式、新语句、新声明，还是调整已有规则？ |
| 文法变化 | 原规则、修改后的完整规则、增量规则；哪些候选式保留或删除？ |
| 词法形式 | 新关键字/符号、token 输出名；是否与已有 token 共享前缀？ |
| 可出现位置 | 条件、初始化、实参、返回、数组下标、常量初值、数组长度等 |
| 优先级与结合性 | 高于/低于哪一层；左结合、右结合，还是禁止连续使用？ |
| 类型规则 | 允许哪些操作数类型、是否转换、结果是什么类型？ |
| 目标要求 | 普通值、变量、数组元素、可写左值，还是整个数组？ |
| 作用域 | 是否引入名字或作用域；声明何时可见、何时失效？ |
| 控制流 | 是否改变 break/continue/return 的合法范围或执行顺序？ |
| 副作用 | 是否修改状态；目标地址和操作数各求值几次？ |
| 常量上下文 | 能否用于常量初值/数组长度；允许时怎样计算，禁止时怎样诊断？ |
| 错误策略 | 不合法输入在哪个阶段拒绝、报什么、定位到哪里、能否恢复？ |
| 兼容性 | 会改变哪些原有程序的 token、解析结果、语义或输出？ |
| 验收方式 | 合法例、非法例、边界例和对应的独立预期答案 |

例如 `a OP b` 的文法成立，并不意味着 `int OP char` 合法，也不意味着结果一定为 `int`。项目采用严格类型检查，不能直接套用 C/Java 的隐式转换规则。

新增关键字还会影响已有标识符：把 `repeat` 变成关键字后，原来的 `int repeat;` 可能变为非法，必须将这类变化写入兼容性说明。

## 2. 根据扩展种类确定修改范围

不是每次都要修改所有文件。先确定变化落在哪些层，再列清单。

| 扩展种类 | 通常需要修改 | 重点检查 |
| --- | --- | --- |
| 已有优先级层加入一个运算符 | token/lexer（如有新符号）、解析分支、类型与常量运算 | 操作数约束是否真的和该层其它运算符相同 |
| 新增表达式优先级层 | 新 AST 类、上下层 AST 构造器、Parser、Traverser 分发、常量求值 | 上下游有没有完整接通 |
| 新增前置/后置表达式 | token/lexer、表达式 AST、Parser、语义检查 | 表达式入口、可修改目标、结果类型、副作用 |
| 新增控制语句 | 关键字、Stmt AST、parseStmt、visitStmt | 作用域、嵌套、跳转目标、恢复位置 |
| 新增声明或限定符 | Decl/BType/VarDecl 等入口、声明 AST、符号与类型处理 | 全局/局部可见性、初始化、同名规则 |
| 新增类型或函数规则 | 类型表示、兼容性、声明/调用、符号、输出与常量表示 | 参数匹配、存储大小、返回值；通常影响范围更大 |
| 仅调整已有形式的语义 | 语义分析、诊断、常量求值、参考答案 | 不应为语义差异随意改词法或文法 |

| 解析输出/回溯 | `src/frontend/ParserWatcher.java`、`src/utils/BackTrace.java` | 输出轨迹与投机解析状态 |
| 语义 | `src/frontend/Traverser.java` | 类型、名称、上下文、控制流与诊断 |

| 驱动 | `src/utils/Controller.java`、`HomeworkConfig.java` | 阶段选择、正式输出；普通扩展一般无需修改 |

| 测试参考 | `testgen/sysy.ebnf`、`oracle.py`、`boundaries.py` | 独立文法、语义契约和专属边界 |

## 3. 设计文法：先明确入口、优先级和歧义

### 3.1 写完整规则，再决定如何提交增量

文法直接写，不需要 `// ` 前导：

```text
UnaryExp -> '++' LVal | LVal '++'
```

这可以表示“追加两个候选式”，不应误解为 UnaryExp 只剩这两种形式。若是替换规则，必须写出替换后要保留的全部候选式。

`testgen` 默认合并同名规则并去重，`--replace` 则替换输入中出现的同名规则。新增优先级层时尤其要注意：保留旧的下层入口，可能产生绕过新层的解析路径和歧义。

### 3.2 放在已有层，还是新增一层

当前主要表达式关系如下，向右通常结合得更紧：

```text
Cond -> LOrExp -> LAndExp -> EqExp -> RelExp -> AddExp -> MulExp -> UnaryExp
Exp      -> AddExp
ConstExp -> AddExp
PrimaryExp -> '(' Exp ')' | LVal | Number
```

因此只在 EqExp 加入规则，并不会让它自动出现在普通赋值右侧或实参中；括号里的 `Exp` 也不会自动扩大为 `Cond`。每条新规则都应检查从所需入口到它是否存在路径。

如果新运算符与乘除同优先级，可考虑扩展 MulExp；如果要有独立优先级，应增加一层。例如下面是**示例设计**，规定 `**` 左结合、比乘除更紧，且 UnaryExp 比它更紧：

```text
PowerExp -> UnaryExp | PowerExp '**' UnaryExp
MulExp   -> PowerExp | MulExp ('*' | '/' | '%') PowerExp
```

这意味着 `a ** b ** c` 为 `(a ** b) ** c`，`-a ** b` 为 `(-a) ** b`。这是该示例的选择，不能因为符号像“幂”就默认其它语言的规则。

如果希望右结合，则可设计为：

```text
PowerExp -> UnaryExp ['**' PowerExp]
```

同时说明单目负号与幂的优先级是否也要改变。结合性和优先级是两个独立问题。

### 3.3 提前确定消歧规则

常见冲突包括：

- `Ident` 开头的变量、数组、函数调用、赋值和后置表达式。
- `(` 开头的括号表达式、强转，未来可能还有类型名。
- 嵌套 if 的 else 归属；本项目按最近的 if 匹配。
- 新符号与旧符号共享前缀，导致旧输入的 token 切分改变。

明确使用多少前看、是否需要回溯，以及“语法上允许但语义不合法”和“语法直接禁止”的边界。例如目标限制为 LVal，还是允许一般 Exp 后再检查可写性，会影响 AST 和非法输入的诊断阶段。

## 4. 词法层：识别新 token，并保持位置准确

新增一个词法形式时，依次检查：

1. `TokenType` 是否有独立枚举与明确的输出名。
2. 新单词是否应进入 `Keywords.TABLE`；新单字符是否进入 `Symbols.TABLE`。
3. 多字符符号是否需要 `Lexer.readOp()` 的专门分支。
4. 向前读取失败时是否正确回退，包括文件末尾。
5. token 的位置是否指向约定的起点。

`Symbols.TABLE` 的键是 Character，不能向其中直接添加 `"++"` 或 `"**"`。如果以后加入三字符以上运算符，应按所有共享前缀设计扫描顺序，不能只补一个双字符判断。

边界必须同时测：完整符号、单独前缀、连续相邻、插入空格、插入注释、紧接 EOF、出现在字符串/字符/注释里。例如：

```text
x+++y
x + ++y
x+/* gap */+y
```

按已定义的 token 集做最长匹配，但不能跨空白或注释合并。词法扫描只确定 token，不负责判断“常量能不能修改”等语义。

## 5. AST 与解析层：完整保存结构并接通所有入口

### 5.1 AST 应保存后续阶段真正需要的信息

一般需要：操作数、运算符 token、关键字/结束位置、子语句，以及前置/后置等不同形态。引用变量的节点可沿用已有符号绑定机制。

同一非终结符的不同形式可通过 Kind 区分；新增优先级层通常需要独立节点。不要为了少建节点而丢掉影响语义或输出的区别。

新增 Kind 或类型后，搜索所有枚举 switch 和 instanceof 分发。Java 编译能发现部分穷举遗漏，但 `analyzeOperand()` 这类带兜底返回的分发可能静默漏掉新节点。

### 5.2 左结合用循环，右结合按右侧递归

手写递归下降不能直接调用尚未消费 token 的自身来处理左递归。左结合层通常先读一个操作数，再循环累积节点。

下面是上述左结合幂规则的**解析骨架**，依赖待添加的 `PowerExp` 类和示例 token `TokenType.Power`，不是当前可直接粘贴编译的补丁：

```java
private PowerExp parsePowerExp() {
    PowerExp exp = watch(new PowerExp(parseUnaryExp()));
    while (among(TokenType.Power)) {
        Token op = consume(TokenType.Power);
        exp = watch(new PowerExp(exp, op, parseUnaryExp()));
    }
    return exp;
}
```

还需将 `parseMulExp()` 首个操作数和每个右操作数都改为 `parsePowerExp()`，同步 MulExp 构造器类型。新节点继承 BinaryExp 时，还要为其运算补齐类型与常量运算逻辑。

右结合规则通常只消费一次该层运算符，并在右操作数处调用本层解析。禁止连写的运算符则应明确检测第二个同层运算符，而不是悄悄解析成左结合。

### 5.3 不要漏掉入口判断

| 功能变化 | 当前需要检查的位置 |
| --- | --- |
| 新表达式首 token | `atExpressionStart()`；首个实参、return、数组长度等使用点 |
| 新语句关键字 | `parseStmt()`；是否与声明/表达式分支竞争 |
| 新声明、类型、限定符 | `parse()` 的顶层判断、`parseDecl()`、`parseBlockItem()`、`parseBType()` 等 |
| 新后置形式 | 变量/数组/函数调用的判断顺序；`isAssignStmt()` 的分类 |
| 新非终结符 | 所有应调用它的上层入口和 AST 构造器 |

只让独立的 `newExpr;` 能解析还不够，还要分别测 `return newExpr;`、首个实参、初始化、条件、下标等已承诺支持的位置。

### 5.4 投机解析要回滚全部状态

本项目通过 BackTrace 同时保存 token 流、错误表和 watcher。投机解析不能残留重复 token、非终结符或诊断，状态恢复宜放在 finally 中。

若新增投机操作会覆盖已有条目，需确认快照能真正恢复这种修改。当前 ErrorTable 快照按列表长度恢复，并不等于保存了所有条目内容；不能将“回滚新增项”泛化为任意状态都可回滚。

### 5.5 解析输出也是接口

`parser.txt` 是 token 消费与 `watch()` 的记录：通常先输出子结构，再输出当前非终结符。新增层会改变文本轨迹，需事先决定是否输出 `<NewExp>`。

原有普通表达式的包装层不能随意省略；同一层的左结合累积节点也需按约定输出。`Decl`、`BType`、`BlockItem` 当前不输出标签。参考生成器的 `--hide` 仅用于明确的输出约定，不能用来掩盖 AST 层次错误。

## 6. 语义层：沿用上下文，明确类型和目标约束

### 6.1 新表达式通常按这个顺序分析

```text
分析必要子节点并传递上下文
    -> 解析名字与符号
    -> 检查操作数类型和目标可写性
    -> 检查常量/条件等上下文限制
    -> 确定结果类型并记录诊断
    -> 按项目约定缓存类型、返回结果
```

在 `Traverser` 中，新二元层要接入 `analyzeOperand()` 等分发；新 UnaryExp.Kind 要接入 `analyzeUnaryExp()`；新语句要接入 `visitStmt()`。仅新增一个 `analyzeXxx()` 方法而没有调用路径，不会生效。

现有 `analyzeBinary()` 的同类型基本操作数检查，以及 `put()` 对类型缓存和字符结果的处理，可以在语义相同时复用。不同操作符若约束不同，应单独分发，不能只因 AST 都是 BinaryExp 就一律使用同一规则。

子节点已报错且返回 null 时，应抑制没有意义的连锁错误；另一方面，当前部分分析会在报错后仍返回类型，因此“返回值非空”不等于该表达式完全合法。

### 6.2 读值、写目标、整个数组要分清

写操作除了检查类型，还应检查：名字确实是变量、目标可写、不是常量、是否允许数组整体，以及下标是否合法。即使 `x OP;` 是表达式语句，也不能依赖 `analyzeAssign()` 替它检查常量修改。

现有 `analyzeLVal()` 可复用名称、符号绑定和下标检查，但是否处于常量上下文、是否允许写入仍由新规则决定。对 `a[f()]` 这类目标，运行时必须考虑地址计算次数。

### 6.3 新语句的上下文要成对进入和退出

- 新块按规则调用 `symbols.newScope()` / `exitScope()`，退出后名字不可见。
- 循环控制分别考虑 `loopDepth` 与 `breakDepth`：switch 允许 break，却不能使循环外的 continue 合法。
- 新函数形式要维护返回类型、参数作用域和返回检查。
- 临时修改条件上下文、深度或作用域时，应保证异常路径也能恢复。

静态分析仍应检查所有需要检查的分支。运行时会短路或不会执行的分支，不因此自动免除名称、类型和其它静态约束。

### 6.4 类型缓存必须与上下文一致

当前类型缓存按 AST 节点身份保存。新功能若使同一节点在不同上下文中具有不同合法性或结果，需重新审视缓存策略，避免第一次分析的缓存跳过第二次上下文检查。不要在多个语法位置随意共享一个可变 AST 节点。

## 7. 常量求值与未来代码生成分别处理

### 7.1 纯运算

若允许编译期计算，需要补齐 `calculateConst()` / `ConstValue.calculate()` 等入口，并规定除零、溢出、移位或新运算的定义域。

本项目通过语义信息决定字符结果，BinaryExp 可在每一步按 `& 0xFF` 截断。新增运算如果保持这一规则，应确保逐步计算一致；若要改变，必须同时更新规范和参考答案。

### 7.2 有副作用的运算

赋值、自增、调用等不能为方便而直接改变语义分析器中记录的变量值。先规定其常量上下文合法性；禁止时显式诊断，并阻止将其折叠成合法常量。

`ConstFolder.fold()` 会捕获 RuntimeException 并返回 null。这只表示没算出常量，不等于已经输出了用户需要的错误。

### 7.3 后端存在后再验收执行语义

对写操作通常需要：求地址一次、读取旧值、计算新值、写回，并返回约定的新值或旧值。例如不能在未确认求值次数和顺序时直接将 `a[i++] += f()` 展开成重复出现目标的赋值。

对新循环要定义 continue 的跳转位置；对条件/逻辑表达式要保持短路；对新类型要定义表示和存储。以上是未来实现要求，当前前端成功不代表程序执行结果已正确。

## 8. 错误诊断与恢复也属于扩展规范

为每类非法输入记录“阶段、错误码、位置、恢复动作”。现有对应关系为：

| 错误码 | 含义 |
| --- | --- |
| a | 非法 token |
| b / c | 重复声明 / 未定义引用 |
| d / e | 参数数量 / 项目约定的类型不匹配 |
| f / g | void 函数带值返回 / 缺少规定的 return |
| h | 修改常量 |
| i / j / k | 缺少分号 / 右圆括号 / 右方括号 |
| l / m / n | printf 数量不匹配 / 非法跳转 / 重复 case 或 default |

具体使用须遵循课程文档；不能把所有新增非法情况都套成 e 或 a。若需要新的诊断类别，单独说明扩展错误码、优先级及其与原课程提交的兼容方式，并同步 `DisplayError` 的枚举 switch。

当前 `consume()` 仅对 `;`、`)`、`]` 缺失提供既有恢复。任意非法表达式可能中止解析，并不保证有通用错误码；`Controller` 捕获异常、输出错误表，也不代表已经生成了有效诊断。

新恢复策略应定义同步点，例如分号、块结束或下一个 case；检查 EOF、空节点和向前推进，避免死循环或 NullPointerException。缺少 token 时不要把“插入的概念 token”当作原输入 token 输出。

同一行当前只保留一条错误：a 优先级 30，i/j/k 为 20，其它为 10；同优先级保留先记录项。因此单错误测试先独立分行，再专门测试错误组合和行号。

## 9. 测试：合法一侧与非法一侧都要覆盖

### 9.1 每个新功能至少检查这些维度

| 维度 | 测试内容 |
| --- | --- |
| 最小合法例 | 最短写法、空项/可选项、单次使用 |
| 词法边界 | 共享前缀、连续字符、空白/注释、EOF、字面量内的相同字符 |
| 结构组合 | 同层连写、左右结合、上下层优先级、括号、嵌套 |
| 嵌入位置 | 语句、初始化、实参首项与后续项、返回、条件、下标、常量位置 |
| 类型与目标 | int/char、标量/数组/元素/函数/void、变量/常量、未定义目标 |
| 名称与作用域 | 全局/局部、遮蔽/重名、先使用后声明、离开作用域 |
| 控制流 | 嵌套循环/switch、break/continue、分支与返回 |
| 数值边界 | 0/1、int32 极值、字符边界；先区分静态错误与运行时定义域 |
| 错误恢复 | 缺操作数/分隔符、截断输入、多行错误、同一行优先级 |
| 压力与回归 | 长链、深嵌套、大参数量；旧文法与官方样例 |

优先做有理由的成对和高风险组合，再加入有界随机测试；仅增加随机数量不能保证碰到关键边界。

### 9.2 预期答案要独立于待测实现

合法前端用例可有 lexer/parser/symbol 和空 error 预期；语义错误用例明确错误码与行号；非法语法若没有通用错误码，明确要求语法拒绝，不伪造答案。普通崩溃不能充当正确拒绝。

官方答案可直接使用；一致重命名、前置空行等变体要同步更新答案。前端检查和运行时输出应分开，尤其不能用有未定义求值顺序、越界或除零的程序验证运行时结果。

### 9.3 使用本项目 testgen

示例命令从项目根执行，输出目录须为新目录或空目录，规则无需 `// ` 前导：

```powershell
# 新增 ++：随机部分 + 基础边界 + 已定义的 ++ 专属边界
python -m testgen --suite mixed --rule "UnaryExp -> '++' LVal | LVal '++'" --count 30 --scale 2 --out build/grammar-inc-review

# 已有幂示例：替换 MulExp，提供 token 名和类型契约
python -m testgen --suite mixed --rules testgen/examples/power.ebnf --replace --focus PowerExp --tokens testgen/examples/power-tokens.json --semantics testgen/examples/power-semantics.json --count 30 --out build/grammar-power-review

# 尚无语义契约的独立规则：只检查片段结构
python -m testgen --mode syntax --rule "Pair -> '(' IntConst ',' IntConst ')'" --count 10 --out build/grammar-pair-review
```

`same` 二元契约要求操作数为相同基本类型，结果沿用该类型；`int` 契约同样要求相同基本类型，结果为 int。它们只定义类型，不自动定义运行时运算。

| 新规则的变化 | 生成器需要同步的位置 |
| --- | --- |
| 规则与优先级 | 增量 EBNF；如果修改正式基线，再同步 `sysy.ebnf` |
| 新终结符 | `--tokens` 映射或 `oracle.py` 中的正式 token 定义；新字面量类别还需扩展扫描器/文法类别 |
| 简单二元类型规则 | `--semantics`；不在现有契约内时扩展独立语义模型 |
| 新声明/作用域/语句 | `oracle.py` 的对应语义方法，以及完整程序嵌入上下文 |
| 新 AST 标签约定 | 独立解析输出规则；按明确规范使用 `--hide` |
| 专属极端情况 | `boundaries.py` 的 `extension_fixtures()`，必要时适配 `symbol_inventory()` 等参考逻辑 |

任意 BNF 不能自动生成可靠的 symbol/error 答案。未知语义应补充契约或使用片段模式；已有边界模板也不能证明任意新类型/作用域规则正确。

实现后可追加 `--check --jdk '你的 JDK 安装目录'`，或使用 `--check-only --out 批次目录 --jdk ...` 回归已有完整程序批次。查看 manifest 中的实际产生式、终结符、标签与未覆盖项，而不仅是调度次数。产生式全覆盖不等于语义、组合或执行路径完备。

## 10. 构建、交付与文档模板

实现时按“规范 → 文件清单 → token → AST/解析 → 语义/常量 → 输出/UI → 回归”的顺序推进，每一步都检查前后层连接。

需要构建核心和 UI 时，在 Windows 使用 `./run.bat --build-only`，macOS/Linux 使用 `./run.sh --build-only`，需要 JDK 17+。只改文档时无需重新构建或生成大量测试产物。

扩展实现的完成条件：

- 文法、优先级、类型、副作用、常量上下文和错误规则已明确。
- 新结构能从全部承诺的入口到达；AST/遍历没有遗漏。
- lexer/parser/symbol/error 的格式、位置和诊断符合约定。
- 新功能的合法、非法、边界、恢复用例与旧文法回归已有结果。
- UI 与参考模型已按影响范围同步，限制和未实现阶段如实记录。

以后每个具体扩展可单独建 `docs/文法扩展-功能名.md`，复制以下结构：

```markdown
# 文法扩展：功能名

## 1. 功能与状态
当前实现了什么；本文是方案还是已实现说明。

## 2. 规则契约
原规则、完整新规则、增量规则；优先级、结合性、类型、目标、
作用域、副作用、常量上下文、错误码与兼容性。

## 3. 修改文件清单
文件 | 必须/按条件/无需修改 | 具体方法 | 修改理由

## 4. 分层改动
词法 -> AST -> Parser/入口/输出 -> Traverser/上下文 -> 常量 -> UI。
给出关键方法的完整拟定代码及依赖；示意骨架须明确标注。

## 5. 测试与独立预期
完整输入、预期阶段产物、错误行号、边界与恢复；明确参考来源。

## 6. 构建与验证结果
可复现命令、实际运行结果、已知差异和未覆盖项。

## 7. 后续运行时要求
若后端未实现，记录求值顺序、地址次数、写回、短路等要求。
```

若当前任务只要求方案，将改动清单和关键方法代码写入上述文档即可；不要把“建议改法”表述为已经修改、编译或验证通过。
